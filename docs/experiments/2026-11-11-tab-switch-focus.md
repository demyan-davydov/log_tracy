# Задержка при переключении табов: фокус внутри нажатия

## Вопрос

С 3–4 крупными логами переключение табов заметно тормозит. Откуда задержка и от чего она
растёт?

## Условия

- 2026-11-11, `master` `9bce476`, debug-сборка (ldc2), Sciter 6.0.5.5, macOS, окно 1000×800.
- Логи: два с флешки (exFAT): `20250505…richos.dlt` (15,6 ГБ, всё время загружался) и
  `Offline_244…Konv.DLT` (0,48 ГБ, длинные payload: медиана 99, 90% — 641, максимум 2324
  символа) с фильтром `speech.dlf`; два с диска: `build/bench/1g.dlt` и `cyr.dlt`.
- Замеры — настоящие клики пользователя: временные метки в `mousedown` таба, в `refreshTabs`,
  `DocumentPane.show()`/`refresh()`, на `mouseup` и в первых кадрах (`requestAnimationFrame`).
  Режимы переключались через отладочный канал (`scripts/app.mjs eval`), не меняя сборку.
  Профиль главного потока — `sample`; цифры при нём завышены (он останавливает потоки),
  сравнивались только прогоны без него.
- Синтетика (переключение вызовом `onDocumentOpened` из `eval`) настоящий клик не
  воспроизводит: она давала 25–50 мс там, где клик давал 200–300.

## Данные

От нажатия до первого кадра, по 8–20 кликов на режим, одна сессия на сравнение:

| Режим | Кадр, мс |
|---|---:|
| Как было: `show()` ставит фокус на таблицу внутри `mousedown` | 200–310 |
| Без фокуса в `show()` | 51–87 |
| Без подготовки перетаскивания (`beginDrag`) | 214–288 |
| Без фокуса и без перетаскивания | 41–59 |
| Фокус после первого кадра | 160–350 |
| Фокус на `mouseup` | 215–322 |
| Обработка нажатия в фазе погружения (`^mousedown`) | 200–250 |
| Без правил `tbody:focus > tr` в CSS | 200–310 |
| Полоса табов фокусируемая (`tabindex="0"`), фокус на таблицу на `mouseup` | 46–93 |
| Итоговое исправление (`press-focus.js`) | 46–117 (один первый показ — 375) |

Наблюдения:

- В `mousedown` таба фокуса уже нет (`:focus` = null) — Sciter сбрасывает его до любого
  обработчика, в том числе в фазе погружения. Фокус, поставленный обработчиком, к `mouseup`
  тоже сброшен: клавиатура после клика по табу никуда не попадала.
- По профилю: `state.focus = true` → `commit_update` → синхронная раскладка панели (~40 мс в
  обработчике), после обработчика — `update_queue::update` → `determine_style` /
  `apply_variables` (~150 мс).
- Фокус после кадра или на `mouseup` дешёв сам (4–13 мс), но следующее нажатие начинается со
  сфокусированной таблицы, и сброс фокуса Sciter-ом при нажатии стоит столько же.
- С фокусируемой полосой табов нажатие переносит фокус с таблицы на полосу (дёшево), и
  фокус на таблицу на `mouseup` стоит 2–10 мс.

Отдельно от фокуса (не исправлено):

- Таблица держит в DOM окно Sciter в 160 строк при 10–25 видимых. На `Offline_244…` полная
  раскладка этих строк — ~95 мс (высота 28 693 px при 484 видимых), однострочный режим не
  помогает: время уходит на текст.
- Если документ догрузился или перефильтровался, пока таб был скрыт, первый показ
  перестраивает таблицу: 150–200 мс.
- Полный пересчёт стилей документа (смена класса у `body`) растёт с числом панелей: ~65 мс с
  одной панелью в DOM, ~165 мс с четырьмя (~6000 элементов); скрытые `display: none` панели в
  него входят. Вынести скрытые панели из DOM нельзя в лоб: при возврате Sciter создаёт
  прототип `tbody` заново — пропадают `docId`, колонки, выделение, прокрутка.

## Результат

Задержку давала смена фокуса таблицы внутри нажатия на таб (и её сброс в «никуда» самим
Sciter), а не данные, носитель или фильтры. Почему внутри события мыши это в разы дороже, чем
из скрипта, видно только изнутри Sciter.

## Решение

Полоса табов фокусируемая (`tabindex="0"`); панель, показанная нажатием на таб, получает фокус,
когда нажатие кончается (`resources/press-focus.js`). Переключение — 46–117 мс, клавиатура после
клика в таблице документа.
