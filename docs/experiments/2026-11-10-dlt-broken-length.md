# DLT: как не дать сломанной длине накрыть следующие записи

## Вопрос

Запись DLT, у которой длина в стандартном заголовке больше настоящей, накрывает следующие
записи: сканер верит длине и ищет следующий storage header только за ней. Как находить
следующую запись, не замедлив сканирование целых файлов?

## Условия

- Apple M1 Pro, файл в кэше, ldc2 1.43.0.
- Варианты (часть 1): замеры ракурса производительности ревью в истории `log-generator`,
  сканирование без декодирования. Программы замера не сохранены, повторить их нельзя;
  дата — до 2026-11-10.
- Выбранный вариант (часть 2): 2026-11-10, ветка `dlt-broken-length` против `master`
  (`947750f`), `node scripts/build.mjs bench <log> --bench index --runs N --json <file>`.
  Строка `offsets` — построение индекса смещений, медиана прогонов. Логи пишет генератор:
  - целый: лог `bench` по умолчанию (`build/tools/bench-dlt-256M-seed1.dlt`: DLT, 256 МБ,
    seed 1), 5 прогонов;
  - `gen-log <file> --format dlt --size 100M --corrupt 0.1%` (все виды порчи), 3 прогона;
  - `gen-log <file> --format dlt --size 100M --corrupt 0.1% --corruptions bad-length`
    (867 сломанных длин, всего 872 801 запись), 3 прогона.

## Данные

Часть 1: варианты.

| Вариант | 1 ГБ сгенерированный | 35 МБ настоящий |
|---|---|---|
| до правки | 53 мс | 1 мс |
| поиск `DLT\x01/\x02` внутри каждой записи побайтно | ~503 мс | 19 мс |
| то же через `memchr('D')` | ~174 мс | 10 мс |
| проверка за O(1): за записью storage header или конец данных | ~66 мс | 2 мс |

Часть 2: выбранный вариант (проверка за O(1), поиск только в сломанной записи).

| Лог | Записей: master → ветка | Индекс, мс: master → ветка |
|---|---|---|
| целый, 256 МБ | те же | 40,4 → 41,5 (+2,7%, в пределах разброса) |
| 100 МБ, все виды порчи | 839 491 → 872 435 | 17,8 → 17,7 |
| 100 МБ, только длина | 760 920 → 871 869 | 15,2 → 17,7 |

## Результат

- Проверка за O(1) почти бесплатна для целого файла: оценка отдельным проходом давала +20%,
  в индексации с её потоком вышло +2,7% (в пределах разброса прогонов).
- На логе с порчей длины индекс строится дольше на 16%, но и записей в нём на 15% больше:
  время на запись то же, поиск внутри сломанных записей в замере не виден.
- Оговорки: части 1 и 2 мерили разными программами; часть 1 не повторить; три прогона на
  порченых логах — мало для разброса в несколько процентов.

## Решение

Проверка за O(1), шаблон ищется только внутри записи, за которой нет storage header'а
(`docs/stories/dlt-broken-length.md`).
