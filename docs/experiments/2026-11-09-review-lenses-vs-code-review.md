# Ревью по ракурсам против `/code-review`

## Вопрос

Стоит ли ревью по ракурсам (`/review`: правила, производительность и потоки, UX — каждый
отдельным агентом со своим чек-листом) своих токенов рядом с обычным `/code-review`? Что оно
находит такого, чего не находит `/code-review`, сколько стоит и сколько ошибается?

## Условия

- Дата: 2026-11-09. Модель: Claude Opus 5.5 у обоих подходов и у ведущего. Чек-листы ракурсов —
  `.ai/workflows/review-*.md` на коммите `9c432f4` (ветка `review-lenses`).
- Три уже слитые фичи разного характера:

  | Фича | Слияние | Размер | Ракурсы по `scripts/review-lenses.mjs` |
  |---|---|---|---|
  | якоря | `81fdc09` | 17 файлов, +331/−50 | правила, производительность, UX |
  | search-highlight | `566e7cd` | 28 файлов, +1241/−162 | правила, производительность, UX |
  | parallel-indexing | `3d4853b` | 8 файлов, +1049/−219 | правила, производительность |

- `/code-review`: рецепт высокого уровня (8 ракурсов поиска, до 6 кандидатов в каждом,
  дедупликация без проверки, до 10 находок), запущен отдельным агентом, чтобы его токены
  считались так же, как у ракурсов.
- Ракурсы: агенты `rules-reviewer`, `performance-reviewer`, `ux-reviewer`, все ракурсы фичи
  параллельно.
- Для обоих: дифф `X^1..X`, код читается на коммите слияния (`git show X:<path>`), позднейшую
  историю (коммиты после, backlog и истории, написанные позже) смотреть нельзя — чтобы не
  подглядеть известные исправления. Без скриншотов и без бенчмарков.
- Токены и время — из отчётов агентов (`subagent_tokens`, `duration_ms`). У ракурсов время
  фичи — самый медленный из них, раз они идут параллельно.
- Самые сильные уникальные находки проверены ведущим по коду; остальные сравнивались по смыслу
  отчётов.

### Что нашли оба (примерно треть)

- search-highlight: главная таблица перерисовывает все видимые строки на каждом шаге прогресса
  поиска (нашли все четыре прогона по этой фиче); повторный прогон фильтра для закреплённых
  строк; regex на каждую найденную строку в UI-потоке.
- якоря: нет знака «нельзя» при наведении во время поиска; тест назван по старому поведению;
  логика `notice.js` без тестов; анимация на переиспользуемых строках.
- parallel-indexing: многопоточность `LogFilter` нигде не описана; тест падает на 63+ ядрах.

### Только `/code-review` — логика состояния и порядка событий

- search-highlight: цвета чипов нового поиска ставятся раньше, чем меняется фильтр документа;
  второй захват мьютекса на строку (обе уже были в backlog, записаны автором фичи); убранный
  двойной клик (ложная тревога: история описывает замену); устаревший `pressedRow`.
- parallel-indexing: отмена вместе с потерей файла заканчивается ошибкой, а не отменой
  (**проверено**); исключение в `deliver` не останавливает начатые блоки; блоки меряются
  записями, а не байтами; гонка в обработчике потерянного файла на Windows стала шире.
- якоря: `messageIndex < 0` сессия сама превращает в `busy`.

### Только ракурсы — знания проекта и платформы

- производительность, parallel-indexing: в Phobos кеш матчера регулярки — одна запись на поток
  (**проверено**, `std.regex` `matchOnceImpl`): два чередующихся regex-правила пересоздают
  матчер на каждой записи под глобальным замком GC; UI-поток делит процессор со всеми потоками
  скана.
- UX, якоря: ловушки Sciter из `.ai/knowledge/sciter.md` (смена `content` у `:before` — мигание
  строк; модальный popup съедает следующий клик); кружок обрезается при крупном шрифте; контраст
  в темах.
- UX, search-highlight: следование за строкой в скрытую страницу поиска (вкладка File Info);
  найденная строка почти не отличается от неактивного выделения.
- правила: нет теста на упавший поиск; тест остановки не проверяет исход; `docs/performance.md`
  устарел после слияния.

### Точность

- Главную «ошибку» якорей — неверный текст «busy» при загрузке и потере файла — назвали
  `/code-review` и пилотный прогон UX (до сравнения). Второй прогон UX проверил, что в этих
  состояниях таблицы закрыты оверлеями статуса: ошибка видна разве что в гонке в момент потери
  файла (**проверено** ведущим). Задача на её исправление была предложена и снята.
- Ложные тревоги: ракурс правил на якорях — «перерисовка без запроса» (смена метки при
  наведении, которую просили); у `/code-review` — убранный двойной клик.
- Ракурсы помечают уверенность («подтверждено» / «предполагается»), `/code-review` по рецепту —
  нет.

### Пилот (до сравнения)

Ракурс правил на ветке `ai-context` (94 тыс. токенов, 75 с) нашёл три пробела в документации
(нет истории ветки и записи в backlog, устаревшие перечни) и три мелочи в скрипте — все
исправлены. Ракурсы производительности и UX на якорях (78 и 90 тыс. токенов) — те же находки,
что и в сравнении, плюс ложная тревога о перерисовке у UX.

## Результат

- Подходы дополняют друг друга, а не дублируют: общая треть, у каждого свои проверенные
  находки другого рода. `/code-review` сильнее в логике состояний и порядке событий; ракурсы —
  в знании этого проекта и платформы (Sciter, Phobos, `ux.md`, потоки индексации), в полноте
  тестов и документов, и точнее в уверенности.
- Ракурсы дороже по токенам в 1,5 раза; оба ревью вместе — примерно в 2,5 раза дороже одного
  `/code-review`. По времени одинаково: ракурсы идут параллельно.
- Выбор ракурсов по файлам работает: parallel-indexing не трогает интерфейс, UX не запускался.
- Оговорки: три фичи — мало для чисел; находки сравнивались по смыслу отчётов, а проверены по
  коду только самые сильные; часть находок ракурсов — предположения, которые ждут замера или
  запуска.

## Решение

- `/code-review` — на каждое изменение; `/review` — перед слиянием фичи и по запросу, когда
  изменение трогает потоки или интерфейс (`.ai/workflows/review.md`, `.ai/workflows/git.md`).
- Перед флагом «перерисовка без запроса» ракурсы правил и UX сверяются с тем, что просила
  задача (`review-rules.md`, `review-ux.md`).
- Новые находки по трём фичам — в `docs/backlog.md`.
- Повторить при смене модели или заметной правке чек-листов: те же три слияния, те же условия.
