# Мелкие инструменты разработки

## Что

Четыре инструмента из бэклога, каждый заменяет несколько ручных шагов, которые повторялись в
задачах (для людей — `docs/building.md`, команды — `CLAUDE.md`):

- **`node scripts/build.mjs bench [лог] [аргументы] --against master`.** Замер ветки против
  ссылки одной командой: временный worktree ссылки, в него копируется бенчмарк рабочего
  дерева, обе стороны собираются одинаково, прогоны идут по очереди (`--runs`, 3) на одном
  логе, печатается таблица «медиана (разброс)» обеих сторон и разница. `--bench rows|index`,
  `--json` сохраняет все прогоны, после `--` — собственные опции бенчмарка. Лог по умолчанию
  пишет генератор один раз: `build/tools/bench-dlt-256M-seed1.dlt`.
- **`node scripts/build.mjs test --module <файл.d>`** вместо длинной команды ldc2: флаги и пути
  импорта берутся из `dub describe`, программа — в `build/tools/`. При падении сказано, что
  раннер druntime остановился на первом упавшем `unittest` модуля.
- **`node scripts/check-ai-context.mjs`**, запускается и из `build.mjs test`. Берёт из `.ai/`,
  `CLAUDE.md` и `.claude/` всё в обратных кавычках вне блоков кода и проверяет пути (файл или
  папка в репозитории, модуль D по имени в `source/`, файл без пути — по имени где угодно),
  идентификаторы (слово в коде) и опции командной строки (`--x` или `"x"` в коде). Имя
  модуля с членом (`ui/filter_commands.DocumentFilters`) проверяется по частям.
- **`node scripts/backtrace.mjs [pid]`**: `lldb --batch` на macOS, `gdb -batch` на Linux, стеки
  всех потоков в `build/backtrace-<pid>.txt`, процесс продолжает работать. Без pid — копия
  `app.mjs`, иначе единственный `log_tracy`.

## Почему так

- **Бенчмарк один на обе стороны — из рабочего дерева.** Так он и раньше делался по
  `docs/performance.md`: старый код может не иметь новой версии файла, а разные версии
  бенчмарка мерили бы разное. `bench_rows.d` уже собирается против старых checkout'ов через
  `static if`. Поэтому вывод бенчмарков можно было подправить под разбор: у пика памяти
  появилась единица, у сводки `bench_index` — `ms` у каждого числа, память после поиска
  печатается под его строкой.
- **Числа читаются из текста, без особого формата вывода.** Число с единицей (`ms`, `ns/row`,
  `MB`) — метрика; её имя — начало строки до двоеточия и её отрезок между запятыми, точками с
  запятой и скобками, остальные числа отрезка — «…». Строка с отступом получает заголовок над
  ней (`search "failed" › main view, rows only: # ns/row`). Отдельный JSON-вывод бенчмарков
  отвергнут: его надо поддерживать в двух файлах D, а человеку всё равно нужен текст. Первый
  вариант называл число всей строкой — имена памяти выходили в сто знаков.
- **Повтор строки в одном прогоне (раунды `bench_index`) берётся по лучшему, стороны — по
  медиане прогонов.** Лучший из раундов — то же, что «best of 5» в `bench_rows`; медиана
  прогонов отсекает одиночный выброс, разброс показан рядом, чтобы было видно, что разница в
  1–2 % — шум. Разница внутри перекрывающихся разбросов помечается «~ noise».
- **Стороны ходят первыми по очереди, лог перед замером прочитан целиком.** Первый вариант
  всегда запускал сначала `master`: холодная загрузка лога с диска (577 мс против 72 мс из
  кэша) доставалась ему одному, и при `--runs 1–2` ветка выглядела быстрее (линза
  производительности `/review`). Время в бенчмарках теперь с десятыми: целые миллисекунды —
  2–3 % поиска на логе в 256 МБ.
- **LFS в worktree не скачивается** (`GIT_LFS_SKIP_SMUDGE`): бенчмаркам Sciter не нужен.
- **Проверка `.ai/` грубая и без модели.** Ловит переименованный файл, класс, опцию — самые
  частые устаревания; смысл текста не проверяет. Ложные срабатывания первого прогона (34)
  были трёх видов, все закрыты правилами, а не списком: пути вне репозитория (`test_data/`,
  `build/…`, папки Sciter SDK), член модуля через точку, `libs/` (сначала был ошибочно
  исключён из списка файлов). В `allowed` остались только API платформы и Sciter и опции
  git/dub. Собственные файлы проверки в «код» не входят: в её тесте устаревшие имена стоят
  нарочно и иначе нашлись бы. Проверено подстановкой трёх выдуманных имён в `.ai/INDEX.md`.
- **Стеки — отдельный скрипт, а не `run.mjs --backtrace`.** Зависшее приложение обычно
  запущено не из этого терминала (`app.mjs start`, другая копия), скрипту нужен только pid.
  Поиск по `pgrep -x`, а не `-f`: `-f` находил и посторонние процессы, в чьей командной
  строке есть путь проекта. Windows не поддержан: отладчика по умолчанию там нет.
