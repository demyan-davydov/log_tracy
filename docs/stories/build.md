# Порядок в сборке

Ветка: `build`.

Сборка держалась на нескольких разрозненных скриптах: bundle-скрипт на каждую ОС (sh и bat),
проверка компиляции под Windows, тесты под Windows, плюс ручные шаги (положить библиотеку
Sciter рядом с программой и тестами, подписать ее на маке). Программа собиралась в корень
проекта, debug и release перетирали друг друга, бандлы тоже ложились в корень. Bundle-скрипты
вызывали `dub` без `--compiler=ldc2`. Библиотеки Sciter лежали в `libs/` вне git.

## Решение

- Библиотеки Sciter (`libs/`, 134 МБ на все платформы) хранятся в git через LFS:
  `.gitattributes` отдает LFS файлы `.dylib`, `.so`, `.dll` в `libs/`. Версия Sciter записана
  в `libs/VERSION`: биндинг `source/sciter/capi` привязан к API конкретной версии.
- `dub.selections.json` теперь в git: для программы версии зависимостей фиксируются, чтобы
  сборка повторялась.
- Один скрипт сборки на Node (`scripts/build.mjs`): Node уже нужен проекту (`node --test`,
  `i18n-extract.mjs`), и один скрипт работает одинаково на всех ОС, без двух копий логики на sh
  и bat.
  - Режим: debug по умолчанию, release параметром.
  - Параметр — архитектура (x64, arm64), а не платформа: собрать программу для другой ОС
    нельзя (для Windows с мака нет линковки), можно только проверить компиляцию.
  - Сборки лежат в `build/<ос>-<архитектура>-<режим>/` (папка в `.gitignore`), рядом с
    программой скрипт кладет библиотеку Sciter. У каждой сборки свой `settings.json`.
  - Дистрибутивы — в `build/dist/<linux|windows|macos>/`.
  - На маке релиз собирается universal binary (x86_64 и arm64 через `lipo`), debug — только
    под архитектуру машины.
- Версия программы — в одном месте, скрипт подставляет ее в `Info.plist` и `app.rc`.
- Подпись на маке: рядом с дистрибутивом лежит скрипт, который пользователь запускает, чтобы
  снять карантин и подписать (ad-hoc) программу и `libsciter.dylib`.
