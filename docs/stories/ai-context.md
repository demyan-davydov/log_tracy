# Контекст для разработки с ИИ (`.ai/`)

## Что

- Общий контекст репозитория — в `.ai/`, по образцу другого открытого проекта: `knowledge/` (как
  устроен код и откуда начинать изменение), `rules/` (обязательные правила для каждого
  изменения и ревью, разделы Red Flag), `workflows/` (повторяющиеся процессы целиком). Вход —
  `.ai/INDEX.md`; на него ведут `AGENTS.md` (для любых агентов) и `CLAUDE.md`.
- `CLAUDE.md` сокращён с 302 строк до ~100: команды, слои пакетов, соглашения, самые дорогие
  ловушки и указатели «что прочитать перед чем».
- Для Claude Code: агент `rules-reviewer` (`.claude/agents/`) и skills (`.claude/skills/`):
  `/review-rules`, `/add-format`, `/add-backend-call`, `/update-sciter`, `/screenshot`.
- `scripts/screenshot.mjs`: снимок окна приложения с открытым логом (macOS, Windows, Linux на
  X11 и XWayland; на Windows и Linux ещё не запускался). Для него
  приложение открывает при старте файлы из переменной окружения `OPEN_AT_START`.
- `README.md` для людей.

## Почему так

- `CLAUDE.md` целиком загружается в каждую сессию: 300 строк про всё подряд тратят контекст и
  топят важное. `.ai/` читается по частям, по задаче; в `CLAUDE.md` остаётся то, что нужно
  всегда, и ловушки, цена которых слишком высока, чтобы надеяться, что агент откроет нужный
  файл (`out LogMessage`, скрытая таблица логов).
- Знания о проекте, накопленные в личной памяти агента (особенности Sciter, требования к
  интерфейсу, порядок работы с ветками), перенесены в репозиторий: их видят люди и другие
  агенты, у них есть история. В памяти остаётся только личное (язык ответов, «коммит только по
  команде»). Память чистится после слияния ветки в `master`, чтобы сессии на `master` не
  остались без этих знаний.
- Содержание процессов — в `.ai/workflows/`, а не в skills: оно нужно и людям, и другим
  агентам. Skills и агент ревью — тонкие обёртки, которые только отсылают туда.
- Ревью по правилам — отдельный агент со своим контекстом: тот, кто не писал код, находит
  больше. Он дополняет `/code-review` (поиск ошибок), а не заменяет его: проверяет то, чего
  общий ревьюер не знает (границы пакетов, тексты для перевода, истории, backlog). Ревьюер
  только сообщает, исправления решает человек. Первый же пробный прогон нашёл, что для этой
  ветки не было истории и записи в backlog.
- Снимок окна — самое слабое место проверки UI агентом. Решения:
  - копия программы во временной папке со своим `settings.json`: настройки разработчика не
    трогаются, а копия релизной сборки не упирается в замок одной копии;
  - снимается только окно приложения (`screencapture -l`), никогда весь экран: однажды
    снимок экрана захватил браузер пользователя;
  - id окна даёт маленькая программа на Swift (`CGWindowListCopyWindowInfo`), собранная один
    раз в `build/tools/`: в Node нет доступа к списку окон. Из окон процесса берётся
    видимое, обычного слоя и самое большое: у приложения есть невидимые окна слоя 0, они дают
    пустой снимок;
  - лог открывается через `OPEN_AT_START`, как уже были устроены `MENU_BAR_PLATFORM` и
    `PSEUDO_LOCALE`. Прежний способ (дописать `openFile` в копию `script.js`) перестал
    работать, когда ресурсы встроили в программу. Открытие файлов из командной строки — это
    уже возможность для пользователей (и передача файлов первой копии), она в backlog.
  - Windows и Linux отличаются только двумя шагами (окна процесса, снимок окна), остальное
    общее: на Windows — PowerShell с user32 (`EnumWindows`, `PrintWindow`), без установки
    чего-либо; на Linux — `xdotool` и ImageMagick `import` на X11. Приложение там запускается с
    `GDK_BACKEND=x11`: в сессии Wayland оно уходит в XWayland, а чистый Wayland снимать чужое
    окно не даёт;
  - временная копия удаляется после удачного снимка и остаётся при ошибке: её вывод
    объясняет, что пошло не так.
- Inspector Sciter включается переменной `SCITER_DEBUG_MODE=1` (отладочный режим окна), а не в
  каждой отладочной сборке: так решил пользователь. Он для людей; агенту нужен свой канал в
  окно (выполнять JS и получать ответ), он отложен в backlog.
- Переменные окружения для разработки называются по смыслу, без имени приложения
  (`OPEN_AT_START`, `MENU_BAR_PLATFORM`, `PSEUDO_LOCALE`, `SCITER_DEBUG_MODE`), и читаются в
  любой сборке, релизной тоже: так решил пользователь. Исключение будет одно — порт
  отладочного канала (`SCITER_DEBUG_PORT`): он работает только в отладочной сборке.
- `OPEN_AT_START` — по одному пути на строку, а не через разделитель путей, как `PATH`: в
  именах логов часто есть `:` (время).
- Перенос `docs/` по тому же образцу (`user/`, `contributing/`, `development/`) отложен: на
  `docs/building.md` и `docs/performance.md` ссылаются скрипты, CI и истории, а пользы мало.
- Из его правил взято правило о детерминированных тестах; правило «не писать тестов,
  которые проверяют только хранение и форму» пользователь убрал.
