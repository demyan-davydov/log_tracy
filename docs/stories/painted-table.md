# Нарисованная таблица: независимый модуль и план замены DOM-таблиц

Решения пользователя (2026-11-19) — внизу, раздел «Решено». Решение (2026-11-19, спайк `row-paint-d`, `docs/experiments/2026-11-19-painted-rows-d.md`):
таблицы лога рисует нативное поведение на D; в том числе ради интереса и чтобы стереть пул строк с его
синхронизацией. Здесь — как это разложить на задачи, и главное: каким должен быть интерфейс.

## Принцип: таблица как чужая библиотека

Таблица ничего не знает о логах, документах, `AppSession`, фильтрах, якорях и Sciter-окне Log Tracy. Её можно
вынуть в отдельный пакет D, опубликовать и подключить зависимостью (как задумано для алгоритма bidi). Всё, что
нужно от проекта, она получает через интерфейсы; всё, что хочет сообщить, отдаёт событиями.

Три слоя, зависимости только вниз:

```
приложение (ui/): DocumentTableModel, правила окраски, якоря, поиск, настройки  — клей Log Tracy
        ↓
таблица (пакет ptable): модель, раскладка, выделение, ввод, события, стиль     — без Sciter и без логов
        ↓
порты: Canvas, TextMeasurer, Clipboard — интерфейсы (таймеров нет: хост даёт кадры, `Table.tick`); их реализует тонкий адаптер Sciter (sciter/)
```

Логика (раскладка, прокрутка, попадание мыши, выделение, ширины колонок) живёт в слое таблицы и проверяется
тестами с поддельными `TextMeasurer` и `Canvas`. Адаптер Sciter только переводит события Sciter в вызовы таблицы
и вызовы `Canvas` в `Graphics`. Спайк уже устроен близко к этому: `row_layout.d`, `text_selection.d`, `row_cells.d` свободны от
Sciter, а `painted_table.d` (870 строк) смешивает логику, данные документа и Sciter — его и надо разделить.

## Интерфейс (набросок, обсудить)

**Данные (входит).** Таблица спрашивает, не хранит.

- `TableModel`: `rowCount()`; `bool cells(size_t row, ref RowData)` — тексты ячеек и *смысловые метки*, не цвета;
  `uint revision()` и событие «строки изменились» (`rowsChanged(first, last)`, `countChanged`) — для читаемого файла и
  фильтра; `rowId(row)` — устойчивый номер строки (Index), чтобы выделение и якоря переживали прокрутку и смену вида.
- `RowData`: `cells[]` (текст + необязательный `CellKind`), `rowKind` (смысловая метка строки: уровень, найдено, якорь...),
  `fragments[]` (диапазоны текста с метками: совпадения поиска — цвет задаёт стиль, не данные).
- `ColumnDef`: `id`, `title`, `align`, `minWidth`, `payload` (колонка, которая занимает остаток и переносится),
  `autoSize`, `sample` (для оценки ширины). Колонки меняются отдельным событием.

**Стиль и разметка (входит).** Это не «стили» в привычном смысле: у таблицы свои части (заголовок, ячейка, плашка
уровня, метка якоря, ползунок, виртуальная строка-разделитель), свои состояния (выбрана, нечётная, найдена) и свои
свойства (цвет, фон, шрифт, отступы, границы, высота, выравнивание, режим строк). Поэтому — свой небольшой язык
оформления таблицы (рабочее имя **TSS**, «table style sheet»), общий по духу с CSS, но под таблицу; см. раздел ниже.
Данные несут только *смысловые метки*; всё, как это выглядит, — в `TableStyle`, которую собирает TSS.

## Язык оформления таблицы (TSS) и мост от CSS — второй слой, см. «Слои» выше

**Идея.** В данных — классы (метки), в TSS — правила «селектор → свойства», как в CSS, но селекторы про части таблицы.
Каскад простой: специфичность (части и классы), порядок. Не нужен весь CSS: достаточно того, что таблице нужно.

Набросок (не окончательный синтаксис):

```
row                      { background: var(--row); padding: 1 0; min-lines: 1 }
row:odd                  { background: var(--stripe) }
row:selected             { background: var(--selected); color: #000 }
row.found                { background: var(--found) }
row.level-error cell.level { color: var(--error); font-weight: bold }
row.level-fatal cell.level { color: #fff; plate: var(--fatal-bg) 1 4 }      /* плашка: цвет, отступ сверху/снизу, по бокам */
cell                     { padding: 0 3; font: aux; align: right; border-right: 1 var(--border) }
cell.payload             { font: body; align: left; lines: wrap }               /* wrap | single | clamp(3) */
row.virtual.day          { span: all; height: 22; font: header; background: var(--day-bg); lines: single }
header                   { background: var(--header-bg); font: header; height: 21 }
thumb                    { color: rgba(60,60,60,.45); width: 10 }
thumb:hover              { color: rgba(60,60,60,.7) }
```

- **Части:** `row`, `cell` (+ класс колонки), `header`, `thumb`, `selection`, `badge` (метка якоря) — расширяемый набор;
  приложение объявляет свои классы строк и ячеек, таблица их не знает.
- **Свойства:** `color`, `background`, `font` (роль: `aux`, `body`, `header`, `emphasis`; роли заданы в `TableStyle`,
  размер/семейство — свойства), `font-size/weight/style`, `padding`, `border-*`, `height/min-height`, `align`, `plate`
  (плашка за текстом), `span`, `lines` (`single` — одна строка с обрезкой, `wrap` — перенос, `clamp(n)`), `cursor`.
- **Состояния:** `:odd`, `:selected`, `:hover`, `:focus-row`, `:anchored` — таблица ставит сама по своему состоянию; всё
  остальное — классы из данных.
- **Результат трансляции** — скомпилированная `TableStyle` (быстрые таблицы по индексам, без разбора строк на кадре);
  строится один раз при смене темы или стиля.

**Мост от CSS.** Темы остаются в CSS (`theme-light.css`, `theme-dark.css`), одна правда. Две ступени:
1. **Переменные CSS** (`--ptable-...`, имена получаются из TSS по правилу, а не вручную) читаются при смене темы и
   подставляются в `var(...)` правил TSS. Просто и достаточно для цветов, отступов, размеров.
2. **Пробные элементы** (позже, если нужно): для селектора TSS мост создаёт скрытый элемент с такими же классами и читает
   его вычисленный стиль — каскад и наследование делает настоящий CSS. Применять там, где переменных мало.
Сама таблица CSS и Sciter не знает: мост — часть приложения/адаптера и отдаёт ей готовую `TableStyle`.

## Виртуальные строки

Строки, которых нет в логе: разделитель с датой без времени, «начало сессии», метки перерывов. Решение: таблица работает не
со «строками записей», а с **элементами** (`Item`): реальная строка или виртуальная. Модель отдаёт `itemCount()` и по номеру элемента
— `RowData` с `kind: real | virtual` и `span` (на сколько колонок; `all`). Виртуальная строка оформляется тем же TSS
(`row.virtual.day`), её нельзя выбрать/якорить (если не сказано иначе), выделение текста её пропускает или копирует
как одну ячейку (решить). `rowId` реальных строк стабилен, у виртуальных — составной (день и т. п.).
**Цена, о которой надо знать:** границы дней на логе в 8,9 млн записей — это индекс, а не вычисление на лету. Модель
(приложение) строит его фоном (как индексы лога) и отдаёт таблице `itemCount` и отображение элемент ↔ запись; ядро таблицы
о датах ничего не знает. До готовности индекса таблица показывает только реальные строки.

**Заменено (2026-11-18), см. «Прокрутка и дата над строками своего дня» ниже:** для даты виртуальные строки и индекс границ
дней отвергнуты. Пользователь: ядро знает только строки около экрана, индекса по всему логу нет; дата — не отдельная строка, а
отступ над первой строкой нового дня, часть её высоты.

## Режимы строки: однострочный и многострочный

Свойство `lines` в TSS (по колонке, по классу строки, по таблице): `single` (одна строка, обрезка с многоточием, высота
фиксирована — самая дешёвая раскладка, высоты считаются арифметикой, ползунок точный), `wrap` (перенос, как сейчас),
`clamp(n)`. Переключение на лету (настройка, кнопка): кэш строк сбрасывается, позиция сохраняется по `rowId`.

**Раскладка и связь таблиц (общий интерфейс).** Это ваше требование: размеры колонок и горизонтальный скролл можно
связать у любого числа таблиц, не приколачивая гвоздями.

- `ColumnLayout` — самостоятельный объект: ширины колонок по `id`, правило роста («только растёт» / авто / вручную),
  смещение горизонтального скролла, `subscribe(listener)`. Таблица держит ссылку на *любой* `ColumnLayout`.
- Связать таблицы = дать им **один и тот же** `ColumnLayout` (или `ColumnLayoutGroup`, который синхронизирует несколько
  по выбранным свойствам: `{widths, scrollX}`). Верхняя и нижняя таблицы: один объект; две независимые: два объекта.
  Колонка, которой нет в таблице, просто пропускается (у поиска и главного вида могут быть разные колонки).
- Горизонтальный скролл — часть того же объекта, не отдельный механизм.

**События и команды (выходят и входят).**

- Наружу: `rowClicked(row, button, modifiers)`, `cellClicked(row, column)` (якорь — это щелчок по ячейке, решает приложение),
  `selectionChanged`, `rowsRevealed(first, last)` (какие строки на экране; для подгрузки и ленивых данных), `copyRequested`
  (по умолчанию копирует сама), `contextMenuRequested`, `columnResized`.
- Внутрь: `scrollToRow`, `select`, `setSelection`, `invalidate(rows)`, `setStyle`, `setLayout`, `focus`, `selectedText()`.
- Всё событиями/делегатами, без знания о том, кто слушает.

**Порты и расширения.** `Canvas`, `TextMeasurer` (ширина, высота, ascent, перенос), `Clipboard` (таймера нет: кадры хоста); `TextShaper` для
двунаправленного текста (по умолчанию — «слева направо», потом подключается пакет bidi). Всё подменяется в тестах.

## Слои: ядро с художником и надстройка с правилами (уточнение пользователя, 2026-11-19)

Не один сложный язык сразу, а два слоя, нижний годится и один:

1. **Ядро `Table` + `Painter`.** Ядро считает раскладку, прокрутку, колонки, выделение, ввод; рисование каждой части отдаёт
   *художнику* (`Painter`): `paintBackground`, `paintRow`, `paintCell`, `paintHeader`, `paintFooter`, `paintEmpty` (пустое
   место таблицы), `paintFrozenEdge`, `paintThumb`. Наследник или делегат переопределяет только то, что хочет. Для
   Log Tracy можно остановиться на этом слое: свой художник пишется на D в несколько десятков строк.
2. **Надстройка `StyledTable`.** Готовый `Painter`, который читает простые правила оформления: для строки, колонки или
   ячейки (по классам из данных) — отступы, выравнивание, цвет текста, цвет фона, шрифт, плашка, граница, режим строки.
   Это и есть «TSS» из предыдущего раздела, но как **необязательный второй слой с ограниченным набором свойств**. Мост от CSS
   (переменные темы → значения правил) живёт тут и не нужен ядру.

Порядок работы: сначала ядро и художник (достаточно, чтобы заменить DOM-таблицу); `StyledTable` и мост CSS — когда понадобится
гибкая настройка без кода.

## Требования, добавленные позже (обсуждаемые, определяют фронт работ)

- **Скрытие столбцов** (уточнение: имелись в виду столбцы, не строки). Колонку можно скрыть и показать; это свойство
  `ColumnLayout` (`visible` по `id` колонки), поэтому у связанных таблиц скрытие общее, если они делят объект, или
  раздельное, если нет. Скрытая колонка не занимает ширины, не рисуется, не попадает в выделение и в копируемый текст; её
  ширина запоминается, чтобы вернуться. Закреплённые и скрытые колонки сочетаются (закрепить можно только видимую). Скрытие
  меняет ширину Payload, поэтому раскладка строк и кэш переносов пересчитываются; позиция по `rowId` сохраняется. (Скрытие
  *строк* не требуется вообще: это задача внешнего компонента, модель просто не отдаёт скрытые.)
- **Закрепление колонок слева и справа.** Горизонтальный скролл не двигает закреплённые колонки: они всегда видны, как
  заголовок/подвал по вертикали. Задаётся в `ColumnLayout` (`pinLeft: n`, `pinRight: m` или флаг у колонки). Раскладка: область
  закреплённых слева, прокручиваемая середина (клип), закреплённые справа; выделение текста и попадание мыши учитывают эти области.
- **Заголовок и подвал** (`header`, `footer`): строки, которые не прокручиваются по вертикали и прокручиваются по горизонтали
  вместе с телом (закреплённые колонки — на месте). Подвал нужен, например, для итогов и строки состояния («выбрано N»).
- **Отступы таблицы.** Пустое место сверху и снизу тела (и по бокам): при прокрутке до конца между последней строкой и нижней
  границей остаётся зазор. Это пустая область, которую рисует `paintEmpty` (фон, узор, подпись «конец лога»,
  индикатор загрузки следующей части). Параметры: `padding: {top, bottom, left, right}` у таблицы.
- Всё это ложится на раскладку ядра (области: шапка, левые закреплённые, середина, правые закреплённые, подвал, пустые
  зоны) и на `Painter`; общий интерфейс без «гвоздей».

## Ревью и правка после него (2026-11-19)

Ревью по четырём ракурсам (правила, архитектура, производительность, UX) дало сводку; сделано сразу: ядро не читает метки
(`Extra` вместо строк-классов: `RowData.extra`, `CellData.extra`, `ColumnDef.extra`; уровень, «найдено», «якорь» и роль колонки
— договорённость модели и художника в `ui/log_table/marks`); области таблицы (`ptable/regions`: шапка, тело, подвал, отступы,
полоса ползунка) и вызовы `paintFooter`/`paintEmpty`; кэш строк вынесен из `Table` в `ptable/rowcache`; события одним
`TableEvents` с `cellClicked(item, column)` (якорь ставит приложение); виртуальные строки не выбираются и пропускаются
клавишами; `Escape` не съедается без причины; внешний аллокатор (`RCIAllocator` из `std.experimental.allocator`, по
умолчанию C-куча): арена кэша строк, буфер и хеш-таблица в `ptable/memory`; кадр в установившемся режиме не берёт память у
сборщика (тест через `GC.stats().allocatedInCurrentThread`, проверен: с намеренной аллокацией падает); тексты ячеек
модель пишет в переиспользуемый буфер без `idup`; кэш слоёв текста Sciter — на хеш-таблице и арене, без копирования при
поиске; `Placements` пересчитываются только при смене раскладки. Замеры после правки (release, 1g.dlt): прыжок 8,2 мс (пол 8,3),
кадры 17/18/19, кадр D 1,08 мс (p90 1,6), перенос слоем Sciter 0,78 мс, память прежняя.

**Уровни и полоса прокрутки (решение пользователя):** внизу `ptable/viewport` (`RowViewport`: окно на список строк разной высоты,
ничего не знает о колонках, ячейках и полосе; отдаёт `ScrollMetrics` в строках и принимает `scrollToPosition`), над ним сетка (`Table`:
колонки, шапка, подвал, выделение, ввод). Полоса прокрутки — внешняя сущность: ядро её не рисует и не знает (убраны `barWidth`,
`paintThumb`, перехват мыши ползунка); приложение рисует свою (`ui/scroll_thumb` + `LogPainter.paintScrollStrip/Thumb`), позже её
может заменить нативная полоса Sciter, привязанная к тем же метрикам. Таблица сообщает об изменении метрик событием `scrolled`.

Уточнение пользователя: «внешняя» не значит «всегда чужая». Полосу может рисовать следующий слой самой таблицы: необязательный компонент
в `ptable` (`ptable/scrollbar`: `ScrollThumb`, `ScrollBar` с `ScrollBarPainter` и композиция `ScrolledTable` «таблица с полосой» над `Table`; сделано); хост вправе взять её или подключить свою (нативную Sciter). Ядро и `RowViewport`
о полосе по-прежнему ничего не знают.

**Сделано после ревью (ветка `row-paint-d`, 2026-11-18):**

- *События документа.* `AppSession.subscribeViews(docId, ViewListener)`: в момент, когда `takeScriptCalls` ставит
  `onMainViewChanged`/`onSearchViewChanged`, слушатели получают `ViewVersion` вида; смена колонок (Settings, `setColumnLayouts`)
  идёт им же. Правило `dataVersion` (та же версия — строки добавились, новая — всё заново) живёт в `ui/log_table/view_events`
  (`ViewChangeTracker`, чистый, с тестами); `DocumentRows` превращает его в `ModelChange` (`count` от старого числа строк, `everything`,
  `columns`).
- *Разрезание `Table`.* Вопрос пользователя: класс с ~40 полями и шестью параметрами конструктора — это несколько классов в одном, его
  нельзя нормально проверить. Из `Table` вынесены: `ptable/columnset` (колонки модели, flex, маска видимых, раскладка по ширине),
  `ptable/pointer` (`PressTracker` — нажатие, ждущее стать кликом или протяжкой; `SelectionState`), `ptable/navigation` (`Key`, `navigate`),
  `ptable/rowcopy` (текст для буфера). Объекты хоста — одной структурой `TablePorts`. В `Table` осталось ~22 поля и ~770 строк кода;
  правило записано в `.ai/rules/d.md`. Ещё внутри: хит-тесты текста и рисование выделения (`positionAt`, `paintSelectedText`, ~150 строк) —
  им нужны записи кэша и контексты ячеек, их вынос — отдельная задача (нужен узкий интерфейс «что лежит под точкой»).
- *Второй слой.* `ptable/columnar`: `Column!Row` (определение + `text(row, buffer)` + `extra(row)`), `RowSource!Row` (откуда строки),
  `ColumnarModel!Row : TableModel` (пишет только нужные колонки в один буфер, который переиспользуется; ядро не менялось).
  Первый пользователь — таблицы документа (`ui/log_table/document_model`: `documentColumns`, `DocumentRows`, `documentTableModel`):
  и основная, и таблица поиска — один и тот же `ColumnarModel!DocumentItem`, прежняя `DocumentTableModel` удалена. Таблицы одного документа
  получают один `ColumnLayout` (`ui/log_table/paint_target`: `PaintTarget` вместо полей `MainWindow`), так что ширины, скрытые колонки и
  горизонтальная прокрутка у них общие; `paintProtoD(true, "search")` рисует результаты поиска.

**Идея: ячейка — список абстрактных объектов (текст, подсвеченный текст, ...).** Критически: то, что нужно для подсветки, у нас уже есть —
`Fragment[][]` — диапазоны одного текста с непрозрачным `Extra` (цвет чипа, ссылка). Список объектов вместо этого стоил бы дорого:
выделение, копирование, хит-тест, перенос и ширина колонки считаются по *одной* строке со смещениями UTF-16, а из сегментов её пришлось бы
собирать (или у каждого объекта спрашивать длину, ширину и перенос); на каждую ячейку каждой строки получался бы список — это аллокация
в горячем пути, а диапазоны поиска и так приходят готовыми; пересекающиеся подсветки (два чипа на одном слове) в диапазонах естественны,
в сегментах — нет. Объекты нужны для того, что *не текст*: значок, плашка, цветная точка. Для них предлагаю не заменять текст, а
добавить рядом второй массив — «вставки» (`Inline`: позиция в тексте, ширина, `Extra`), которые художник рисует сам, а таблица резервирует
под них место. Делать, когда появится настоящая потребность (якорь пока отдельная колонка).

**Остаётся из ревью:** тёмная тема и мост CSS (задача 3); тесты адаптера Sciter (`sciter_table`, `painted_table`);
контекстное меню, Shift/Cmd-выделение, пустые состояния, курсор, фокус (UX); перенос `paintCopy` в `platform.js`; набор шрифтов от
художника, а не `LogFont` в адаптере; вынос хит-тестов текста из `Table`; события «строка изменилась» (якорь ставит `ModelChange.rows`,
сейчас строка перечитывается только со сменой вида); забывание раскладки закрытого документа (`PaintTarget.forget` пока никто не зовёт).

## Решено (пользователь, 2026-11-19)

1. **Пакет.** Пока не выносим в отдельный репозиторий, но **делаем как отдельный проект**: пакет `source/ptable/` без
   импортов `domain`/`ui`/`sciter`, свой набор тестов, документация интерфейса; граница проверяется как правило пакетов.
2. **Стиль.** Не просто цвета и шрифты, а цвета, шрифты, отступы, элементы оформления, назначаемые гибко ячейкам, строкам и
   виртуальным строкам. Нужен свой язык оформления таблицы, общий по духу с CSS, и мост от обычного CSS/переменных к нему
   (раздел «Язык оформления таблицы»). Ничего не приколачивать гвоздями под текущие требования.
3. **Виртуальные строки** (разделитель с датой без времени и подобное) — в модели таблицы с самого начала. Для даты заменено
   отступом над строкой (2026-11-18, раздел «Прокрутка и дата над строками своего дня»).
4. **Режимы строки:** однострочный и многострочный — оба в первой версии.
5. **Платформы:** проверка на Linux и Windows отдельной задачей не стоит; разбираемся, когда дойдёт.

## Ещё открыто

- **Правила оформления второго слоя: интерфейс, а не язык.** Пользователь спросил, парсим ли мы язык или говорим об
  интерфейсе. Ответ после обсуждения: **интерфейс**. `StyledTable` принимает правила как данные из кода
  (`StyleRule(selector, properties)`, где селектор — имена классов и состояние, свойства — типизированные поля: цвет, фон,
  отступы, выравнивание, шрифт, плашка, режим строки), без разбора текста. CSS-подобный текст, который парсится, — только
  возможное дополнение позже (читать правила из файла/темы), если понадобится; на нём ничего не строится. Мост CSS остаётся
  мостом переменных (значения в правила), не парсером.

Решено дополнительно: **заголовок и подвал — части таблицы** (области раскладки ядра): ширины колонок считаются динамически по
телу, и два независимых компонента пришлось бы связывать «гвоздями». Таблица без тела получается сама, если когда-нибудь
понадобится общая шапка.

## Внешний вид: `Look` и виды изменений (2026-11-18)

Решения после двух проходов архитектора и разговора с пользователем:

- Один источник правды: `ui/look.Look!Palette` держит шрифты и цвет текста (`TextLook`) и палитру слоя; его читают `LogPainter`,
  полоса прокрутки и кэш текста Sciter. Смена сообщает вид: `LookChange.colors` (только перерисовка, раскладка и кэши
  измерений остаются) и `LookChange.metrics` (шрифты, размеры: всё измеренное устарело). Третий вид («геометрия») без
  имени не вводим: держим в уме.
- Цепочка сброса в одном месте, `PaintedTable.lookChanged`: сначала кэши Sciter (`SciterTextCache.setLook`,
  `SciterMeasurer.forget`), потом `Table.restyle(change)`. Список слушателей упорядочен (`ptable/listeners`).
- Слои хоста: `ui/sciter_table` не знает лог, `ui/log_table` не знает Sciter, общее в `ui/look`; тест
  `tests/js/ptable-boundary.test.mjs` держит это.
- Не сделано: чтение цветов из CSS (`resources/paint-look.js`, `setLook` через `paintCall`, при attach), высота
  заголовка и подвала из метрик шрифта, `descent` из слоя текста, `sizePt` в `double`, делегат ширины колонки у
  `ColumnLayout` (две таблицы склеивают показания; явная и подогнанная ширина), якорь прокрутки (механизм в таблице,
  политика делегатом клиента) для смены шрифта и ширины окна, масштабирование (px, pt, em задаёт верхний уровень).

Ширины колонок (сделано): `ColumnLayout` хранит заданную пользователем ширину и подогнанную по тексту отдельно
(`width = max`); перетаскивание границы забывает подогнанную, `resetFit()` забывает её при смене шрифта
(`Table.restyle(metrics)`), `linkLayouts` переносит обе. Формулу подгонки по-прежнему даёт `Painter.cellWidth`
(уровень выше ядра); отдельный делегат ширины колонки не заводили: второго источника ширины пока нет, а `width()` у
раскладки чистая (`pure`), её читает `placeColumns`.

Якорь прокрутки (сделано): `RowViewport.keepPlace(policy)` запоминает место окна до смены высот (шрифт в `restyle(metrics)`,
ширина окна в `resize`), `restorePlace()` ставит его обратно в конце `Table.prepare()`, когда новые высоты известны, до
первой отрисовки, так что мигания нет. Политика выбора места (какая строка, какая точка: верхний край, середина, и где в
окне) приходит от клиента делегатом `Table.anchorPolicy`; по умолчанию верхний край первой видимой строки. Любая прокрутка
после `keepPlace` (`scrollTo`, `scrollBy`, полоса) побеждает. Остаётся: политика «выбранная строка» у клиента.

Заголовок и подвал из метрик (сделано): `TableGeometry.headerHeight` и `headerBaseline` (и `footerBaseline`) равные нулю
или меньше считает таблица по метрикам шрифта заголовка (`Table.resolveGeometry`: строка шрифта плюс отступы, текст по
центру); `LogPainter` отдаёт нули, и заголовок следует за шрифтом при `restyle(metrics)`. Измеритель Sciter теперь
знает строку и `descent` каждого шрифта отдельно (раньше строка одна на все, `descent = 3`). Осталось из «всё
масштабируется»: смещения значка якоря и плашки Fatal в `LogPainter`, минимальные ширины колонок в `ColumnDef`, `sizePt` в `double`.

Цвета и масштаб из CSS (написано, в приложении не проверено): скрипт собирает значения переменных темы
(`resources/paint-look.js`, чистый модуль с тестом) и передаёт D вызовом `paintCall("setLook", json)`; D разбирает цвета
(`ui/log_table/look_json`: `#rgb`, `#rrggbb`, `rgb()`, `rgba()`) и масштаб, и `PaintedTable` меняет общий `Look` (цвета: только
перерисовка; размер шрифта: сброс кэшей и `restyle(metrics)`). Вызывается при старте таблицы и из `setTheme`/`setTableFontSize`
скрипта. Не проверено: что отдаёт `style.variable` для `morph()` и именованных цветов (`bisque`), и успевают ли стили примениться
к моменту чтения; что не разобралось, остаётся прежним цветом. Остались константами: палитра полосы (`thumb`), цвета уровней,
минимальные ширины колонок.

Дробление `Table` по связности (2026-11-18): поля выносятся не механически, а в блоки, внутри которых они логически
связаны и устаревают вместе. Сделано: `TableSpace` (размер, шрифты, регионы), `TableFonts`, `texthit`; `Placement.defIndex`
убрал поиск колонки по строке на каждую ячейку (id остаётся строкой: он общий для раскладки, моделей и событий).
Сделано дальше: `RowView` (контексты строки и ячейки, текст ячейки, ячейки строки в фокусе для `texthit`) и
`TableSelection` (выбранная строка, выбранный текст, нажатие мыши, копирование). Осталось (14 приватных полей против 7):
`RowsEngine` (кэш, колонки, окно, подписки модели и раскладки, `prepare`, `layout`; самый рискованный, после тестов на
`NumbersModel`; сам он тоже должен уложиться в 7 полей, значит, внутри нужно ещё деление: окно строк отдельно от колонок). Структура-носитель для `_model/_layout/...` не
выносится: это механика, а не ответственность.

`RowStore` и `Subscriptions` (сделано): хранилище строк (модель, раскладка, колонки, кэш, шрифты) приводит всё в порядок
зависимостей в `ensure()` и ничего не знает об окне; `Table.prepare` теперь `store.ensure()` и затем синхронизация окна, а
`entry`/`heightOf` зовут только хранилище, так что окно больше не входит в себя из собственного цикла раскладки.
`slotAt` и цикл `layoutSettled` переехали в `RowViewport`, «колонки устарели» в `ColumnSet`, один общий `FakeMeasurer` для
тестов. Осталось: `FramePainter` (рисование, около 100 строк, `_painter`, `_frames`), `TableSpace` с закрытыми полями.

`FramePainter` (сделано): рисование кадра вынесено из `Table`, он ничего не меняет и считает кадры; `TableSpace`
принадлежит `RowStore` (единственный, кто его пишет через `ensure`, `restyle`, `resize`), остальные читают его через
`const`-указатель; `TablePorts` стал модулем `ptable/tableports`, конструктор `RowStore` берёт `(model, layout, ports)`;
ячейки строки для хит-тестов это структура `FocusedRow`, сделанная на месте (без аллокации), `texthit` стал шаблонным
по типу ячеек, а «строка под точкой» одна (`Table.rowUnder`) и первой строкой делает хранилище актуальным. В `Table`
7 приватных полей, каждое со своим смыслом: `_store` (строки и то, от чего они зависят), `_frame` (рисование), `_rows` (как
строку видят художник и хит-тесты), `_viewport` (окно на строки), `_lastMetrics` (что сообщали полосе прокрутки), `_sel`
(что выбрано и копирование), `_ears` (подписки), и 2 публичных (`anchorPolicy`, `events`). Дальше: `PaintedTable` по плану архитектора.

**Выделение нескольких строк** (2026-11-18, план архитектора, решения пользователя). Ядро хранит набор диапазонов строк (`RowRanges`, массив,
замечание о производительности в backlog) и ничего не знает о клавишах: `RowPicks` — набор, якорь, текущая строка и четыре режима выбора
(`Pick`: заменить, продолжить от якоря, переключить, продолжить и добавить), перетаскивание по строкам, клик правой кнопкой. Какие клавиши
какой режим дают, решает верхний уровень (`ui/sciter_table/input`: `pickMode`; Shift, Command на macOS или Control в остальных системах; Control
с главной кнопкой на macOS — контекстный клик, не выбор); Shift со стрелками продолжает выделение. Нажатие с режимом выбирает строку сразу и
дальше тянет по строкам, а не выделяет текст (простое нажатие, как раньше, тянет текст). Простой клик по уже выделенной строке снимал выделение со всех строк, и с неё
тоже (задумка пользователя), но пользователю это показалось непривычным, и пока отключено (`Table.clickRow`: `RowPicks.click(…, false)`). `selected()` —
текущая строка, если она выделена, иначе -1; `rowSelected` сообщает о ней, когда она изменилась. Копирование — все выделенные строки по
порядку, до `copyLimit` знаков. Выбор стрелками показывает строку плавно (глайд на кадрах хоста; без кадров или для далёкой строки сразу), а строка, с которой
идут клавиши, помечена линиями сверху и снизу (`RowState.focused`, цвет `--border-row-current` в обеих темах). Остаётся: выделить все (Cmd+A), контекстное меню нарисованной таблицы, сообщение «скопировано N из M».

**Выбор строк вынесен из `Table`** (2026-11-18, план архитектора, замечание ревью о размере `table.d`). `ptable/rowpicker` — `RowPicker`: выбранные
строки и то, как их выбирает ввод (режим выбора, клик, нажатие с режимом и перетаскивание по строкам, Escape: сначала текст, потом строки,
сообщение хосту о текущей строке). От таблицы ему нужно четыре вещи, он получает их портами (`PickPorts`: виртуальная ли строка, строка на высоте,
показать строку, сообщить хосту) и больше ничего не знает: ни прокрутки, ни модели. Он владеет `TableSelection`, сжавшимся до текста, нажатия и
копирования. Публичный API `Table` не менялся (тонкие делегаты), поэтому тесты `Table`, `ScrolledTable` и хост остались как были. Клик по строке теперь
показывает её тем же путём, что выбор клавишей (`revealRow`).

**Горизонтальная прокрутка** (2026-11-18). Колонки шире окна листаются вбок: `Table.scrollXBy` / `scrollToX` / `scrollMetricsX` (в пикселях, события
`TableEvents.scrolledX`; смещение хранится в общей раскладке колонок и не уходит дальше концов, а раскладка не хранит больше, чем колонки могут
показать). Flex-колонка без переноса (однострочный вид) держит ширину по самой длинной первой строке из строк на экране (`RowStore.fitToWindow`, `RowGrow.needs`), поэтому хвост длинной
строки достижим. Внизу таблицы полоса (`ScrolledTable`, второй `ScrollBar` с `Orientation.horizontal`), только пока колонки не помещаются; она
вычитает свою высоту из высоты таблицы (на следующем кадре после появления: видимость зависит только от ширины, цикла нет). Вводы: трекпад
(`gesturepan` с `deltaX`: движение идёт по той оси, по которой ушло дальше, чтобы боковой дрейф при прокрутке вниз не сдвигал колонки) и колесо с
Shift (`wheelIsAcross`), без инерции. Смещение общее у главной таблицы и поиска (одна раскладка колонок: в старой таблице каждая листалась сама;
если нужно по-старому, смещение придётся вести в таблице, а не в раскладке). Не проверено вживую: горизонтальное колесо мыши (приходит ли
`MOUSE_WHEEL` с отдельной горизонтальной дельтой, `sciter.md` об этом молчит).

**Таблица больше не хранит содержимое строк между кадрами** (2026-11-18, план архитектора, решение пользователя). Строки лежат в
отображённом в память файле: запись стоит ~150 нс, с форматированием ячеек в текст ~1,3 мкс, кадр из 60 строк ~76 мкс, поэтому кэш
содержимого выигрывал 0,1–0,2 мс на кадр и стоил памяти (предел был в строках, а не в байтах) и логики. Теперь: `RowReader` отдаёт строку из
модели в арену, которой владеет вызывающий; `RowWindow` — строки одного прохода (кадра, попаданий мышью между кадрами), в начале следующего прохода
их нет (`beginPass`); `RowGeometry` — высота, число строк, отступ группы и биты смены голов для строк рядом с окном, в кольце, размер которого
выводится из числа видимых строк (четыре окна, не меньше 64, фиксированного предела нет); строка, которой в кольце нет, измеряется (читается,
по её тексту растут колонки, читается строка над ней ради голов групп) и тексты отпускаются. Если провайдер когда-нибудь окажется медленным,
кэш поставим на доступе к данным, перед провайдером, а не в таблице.

**Хит-тесты текста вынесены из `Table`** (2026-11-18, план архитектора принят пользователем). `ptable/rowhits` — `RowHits`
(«что лежит под точкой среди строк на экране»): `positionAt`, `dragPositionAt`, `partAt` (слово или ячейка под точкой для двойного
и тройного щелчка; делает работу `selectAt` за один проход). Три поля — хранилище, окно на строки, `RowView`; только читает: раскладку
строк и выделение по-прежнему ведёт `Table`. Выбранная строка и строка нажатия — параметры, не поля. `RowView` не хранит никто:
конструктор `Table` делает его локальной переменной и отдаёт одну и ту же `FramePainter` и `RowHits`. Подписки на модель и раскладку
перешли к `RowStore` (`Subscriptions(model, layout)`, `listen`, `detach`; `dispose` отписывает), `Table` стала из 7 полей:
`_store`, `_frame`, `_viewport`, `_lastMetrics`, `_sel`, `_motion`, `_hits`.

**Стили колонки** (2026-11-18, план архитектора; пользователь: «стили зашиты в колонки, у каждой колонки свой, и паддинг у Payload другой — это важно»).
`ptable/columnstyle`: `ColumnStyle` в `ColumnDef.style` — `valign` (по умолчанию середина, как у `td` старой таблицы), `padLeft` / `padRight`
(меньше 0 — `TableGeometry.cellPad`), `wrap` (только flex-колонка; без переноса строка в одну линию, обрезанную краем ячейки и жёстким
переводом строки). Смещение по вертикали считает `RowView` (`alignOffset`), ячейка получает `CellContext.top`, текст — `TextPlace.dy`: так
рисование, попадание и прямоугольники выделения не расходятся. Отступ Payload слева (4pt, как в CSS старой таблицы) берётся из переменной
`--payload-pad-left` через `LogSpacing` и кладётся в стиль колонки моделью (`LogColumnLook`), ширина переноса считается из того же стиля
(`ColumnStyle.inner`). Весь стиль колонки лежит в одном месте (требование пользователя): `halign` и `titleHalign` (число и текст справа, уровень по центру,
Payload слева, заголовки по центру, как в старой таблице; их ставит модель лога по виду колонки, `LogPainter` роли для выравнивания не
читает), `minWidth` (был полем `ColumnDef`), `minHeight` (0 — нет). Решения по системе стилей (2026-11-18, план архитектора и замечания пользователя): один тип `CellStyle` с «не задано» у каждого поля;
стиль колонки (`ColumnStyle`) — три таких слота (`cell`, `group` для голов групп, `header` для заголовка) и то, что принадлежит колонке
целиком (`minWidth`, `minHeight`, `wrap`). Цвета и шрифты в стиле — идентификаторы: ядро само разрешает только шрифт (не задан — шрифт
тела или шапки), цвет в палитру превращает художник при рисовании (`LogColor`, `pick`), поэтому смена темы — простая перерисовка. Стили
строк (чёт/нечёт, выбрана, найдена) в ядро не попали: пользователь согласился, что это переусложнение, их рисует художник отдельно
от стилей колонок. Общей базовой линии нет (пользователь сомневался): ячейка стоит в строке по своему `valign`, строка высотой в самую
высокую ячейку (`ColumnLooks`: шрифт колонки, строка и подъём, пересчёт при смене колонок и шрифтов, не в кадре); шапка растёт до
самого высокого заголовка, заголовок и голова группы центрируются по своему шрифту. Выделение и попадание мышью берут высоту строки у
шрифта самой ячейки (`CellText.lineHeight`). `LogPainter` роль колонки для шрифта, выравнивания и цвета не читает: шрифты ставит модель лога
(`logColumns`: мелкий для чисел и текстов, тело для Payload и уровня), роль нужна только для якоря, значка Fatal и градиента правила.
Однострочный вид — настройка `singleLineRows`: `LogTable.singleLine` перечитывает колонки и строки, место сохраняется;
до приложения доходит через `paintSingleLine` (`resources/painted-table-d.js`). Отложено: ширина flex-колонки без переноса не растёт по самому
длинному тексту (в старой таблице растёт и есть горизонтальная прокрутка); перенос в не-flex колонках.

## Прокрутка и дата над строками своего дня (2026-11-18, вторая половина дня)

**Прокрутка.** Инерция тачпада (`ptable/inertia`), плавный шаг колеса и прокат — один `Glide` разной формы; кто двигает строки —
состояние `Scroll` и таблица переходов `next` (`ptable/scrollmotion`, тест на каждую клетку). Правило, как в браузерах и в macOS:
новое действие отменяет анимацию прежнего; колесо, пока пальцы двигаются, не учитывается; вращение колеса, начатое до жеста, прокат
не обрывает; шаг колеса по ходу проката его разгоняет. Пользователь сначала просил «пальцы первыми», потом, изучив другие продукты
(`docs/experiments/2026-11-18-scroll-input-priority.md`), выбрал «новое действие». Простая форма по его слову: `enum` и функция,
не общий автомат. Найдено вживую: окно висло, потому что обработчик кадра снова просил кадр, а Sciter и так шлёт кадры, пока
обработчик отвечает «обработал» (записано в `.ai/knowledge/sciter.md`).

**Дата.** Первый план — виртуальные строки с датой и фоновый индекс границ дней по всему логу — пользователь отверг: ядро знает
только строки около экрана и строку над ними. Второй — полоса над строкой, найденная сравнением соседей — принят, но дата не
отдельная строка ядра, а отступ (margin) над строкой. Как ячейка делится на дату и время, говорит колонка: `CellPartsExtractor`
(`hasHead`, `head`, `body`; имена выбрал пользователь, после `CellSplit`, `CellFormat`, `CellParts`, `CellParser`), не данные
и не соглашение о пробелах в ядре. Кэш строк хранит тело как текст ячейки и голову отдельно; `RowGroups` решает, какая колонка
группирует и начинает ли строка группу; строка над окном читается один раз и остаётся в кэше (падение на долгой протяжке вверх:
указатель в хэш-таблицу кэша смещался, пока в неё добавлялась строка выше). Головы рисуются после шапки: в
отступе — только в ячейке своей колонки, остальное место отступа пустое (решает художник); наверху голова верхних строк стоит на
месте заголовка своей колонки и закрывает только его; у первой строки лога отступа нет. Каждое из этих правил — замечание
пользователя после просмотра вживую. Копирование: `copy(wholeCellsInFull)` — параметр функции, не свойство таблицы (пользователь
настоял: то, что читает одна функция, не хранится в классе); целиком выделенная ячейка — с датой, кусок — как показан.

Отложено (backlog): стиль плашки,
строка без даты внутри дня, таблица без шапки, выделение, перетаскиваемое через отступ, центрирование текста высокой ячейки по
видимой части.

**Несколько колонок с головами** (2026-11-18, проверено вживую). Группируют все колонки с головами: у строки головы каждой и маска
сменившихся (`RowGroups.changes`), отступ — если сменилась хоть одна. Художник получил два вызова вместо одного (`paintGroupBand` —
пустой отступ, `paintGroup` — голова каждой сменившейся колонки в её ячейке): иначе второй вызов закрашивал бы первую голову. В шапке
у каждой колонки своя голова; голова обрезается по блоку колонок, как заголовки; скрытая колонка не группирует. Проверка — демо
`paintD("demo")` (`ui/log_table/demo_model`): день каждые 7 строк, смена каждые 4, раз в 28 строк обе вместе; демо идёт тем же путём,
что и лог (`TableSource.demo`, своя раскладка колонок). Нарисованная таблица привязана к краям контейнера таблицы CSS (иначе при
растягивании окна отставала: `sizechange` приходит только в конце), но снизу оставляет место полосе прогресса под таблицей.

**Стили плашки** (2026-11-18). Цвета группы (`--bg-group`, `--bg-group-plate`, `--group-line-color`, `--text-group-plate`) — в обеих
темах, по умолчанию через `var()` от цветов строк, шапки, границ и текста; место над и под плашкой (`--group-pad-top`,
`--group-pad-bottom`) — на `.log-table` в `table.css`, от темы не зависит. Размеры таблица получает в dip (договорённость с
пользователем): Sciter отдаёт длину любой единицы как число dip, мост передаёт его как есть. Числа живут отдельно от палитры
(`LogSpacing` в `Look`): их смена перемеряет строки, а смена цвета только перерисовывает. Отступление от плана моста выше
(«имена `--ptable-...` получаются из TSS по правилу»): имена заданы вручную как первый шаг — языка оформления ещё нет, правило
имён появится вместе с ним.


**Выделить всё и контекстное меню** (2026-11-19). Cmd+A (macOS) / Ctrl+A (остальные; Ctrl+A на macOS — начало строки, не наше) выделяет все
строки `0..N-1` (`RowPicks.all`): якорь и текущая строка остаются на месте (первая, если их не было), ничего не прокручивается и не
показывается, выделенный текст снимается; Shift со стрелкой дальше идёт от якоря. Заголовки групп остаются в диапазоне: копирование их
пропускает. Контекстное меню: правый клик (на macOS и Ctrl+клик) идёт в скрипт событием `contextmenu`, скрипт зовёт `hitTest` (первая версия
была `contextClick` с ответом 0/1/2, ниже она заменена): строка под точкой, если она выделена, оставляет все выделенные, иначе становится
единственной (`RowPicker.pickForContext`); выделенный текст не снимается. Копирует D, скрипт буфера не касается. Событие `contextmenu`
в Sciter без позиции (x и y равны 0): скрипт берёт её из последнего `mousedown`. Клик по пункту меню приходит в таблицу ещё и как
нажатие левой кнопки с флагом `HANDLED` и сбрасывал выделение текста до копирования: таблица такие события пропускает (`isOurEvent`).
Двойной и тройной клик выделяют слово и ячейку только после нажатия главной кнопки (`startsPickPress`). Обработчики пунктов свои (`paint-copy-*`), со старой
таблицей (`contextList` в `script.js`) ничего не разделено: старая таблица уйдёт целиком. «Скопировано N из M строк» сюда не входит.

**Hit-test вместо меню в таблице** (2026-11-19, по замечанию пользователя). Меню не часть таблицы: таблица отвечает на `hitTest(x, y)`
(`TableHit`: строка, колонка модели, выделена ли строка, есть ли выделенный текст; ничего не меняет), скрипт сам решает, какие пункты
показать («Copy» при тексте, «Copy Cell», «Copy Row»), и при невыделенной строке зовёт `contextPick(row)`. Каждый пункт хранит адрес
(вид, строка, колонка), а копирование идёт по нему: `copy(CopyTarget.text | rows | cell, row, column)`. Прежний `contextClick`
и `copy(rowsOnly)` убраны.

**Ответ hit-теста: виды** (2026-11-19). `hitTest` отвечает видом (`HitKind`): `header` (колонка, строки нет), `footer`, `cell` (строка, колонка,
выделена ли строка, а если точка на самих символах — смещение и слово), `free` (пусто под строками, поля и отступы, таблица без строк;
колонка по x есть всегда). Колонка называется своим `id` (стабильно при перестановке и скрытии); индекс колонки модели идёт рядом
только для вызова `copy`, который следует сразу за ответом (скрипт передаёт числа). Строка — номер элемента модели, не идентификатор записи.
Часть таблицы определяет чистая `areaAt` по `Regions`. Полосы прокрутки хост-стороны и в ответ не попадают. Остаётся: `groupHead`
(голова группы и отступ над первой строкой группы сейчас дают `free`), меню шапки и пустого места (сейчас скрипт их не показывает).

**Содержимое ячейки выходит из ядра** (2026-11-19, решение пользователя; подсветка совпадений в Payload показала, что ядро знает о тексте слишком много:
перенос, измерение, стили, hit-тесты). Виртуальная таблица не должна знать, как рисовать содержимое, и по сути ничего о нём. Принято (с архитектором):

- **Колонка становится интерфейсом (объектом)**: у неё общие свойства (flex, наименьшая ширина, закрепление, выбираемость) и своё поведение. Она сама
  меряет и рисует свои ячейки, свой заголовок и голову группы; стиль лежит в ней самой (у текстовой колонки это `ColumnStyle`), таблица стилей не передаёт.
  `ColumnDef.style` из ядра уйдёт в текстовое содержимое. Промежуточный интерфейс `TableColumn` (`ptable/column.d`, ранее `CellContent`, коммит «the content of a cell is an
  interface of its own») — его первая форма: `measure`, `draw`, `hitTest`, `rects`, `text`, вызовы изменений `rowsChanged`/`widthChanged`/`lookChanged`.
- **Таблица без наследования**: `Table` — конечный класс, всё поведение приходит объектами: модель (данные и колонки), колонки, `Painter` (рамка строк:
  фон, полосатость, границы, поля групп, шапка, подвал), формат копирования (как склеивать ячейки и строки; не в базе). `LogTable` владеет одной таблицей,
  собирает эти объекты и показывает наружу только нужное; наследование не нужно ни у таблицы, ни у логовой таблицы.
- **Выделение в базе — диапазон непрозрачных позиций** (`Position`: строка, колонка, число внутри ячейки, понятное только её содержимому; границы `begin`/`end`).
  База ничего не знает о том, что это за символы. `hitTest`, прямоугольники и текст для копирования даёт колонка.
- **Измерение в духе HTML**: наименьшая ширина по содержимому, естественная ширина (без переноса) и высота при заданной ширине. Два вызова, `measure`
  (только размеры, дёшево и для строк вне экрана) и `layout` (раскладка для рисования и hit-тестов; пишется в арену прохода или в кэш), по настоянию архитектора.
- **Кэш содержимого разрешён**, но не в базе: отдельный класс в логовой таблице, который используют колонки; об изменениях ему сообщают вызовами
  `rowsChanged`/`widthChanged`/`lookChanged` (база их получает от модели), версий и подписок не нужно.
- **Куски текста со стилем** вместо подложек вслепую: текст рисуется кусок за куском через `drawText` на общей базовой линии; перенос считается по кускам с их
  шрифтами. Подсветка совпадений поиска, жирный шрифт и ссылки — одно устройство. Режим абзаца Sciter получает ту же схему: слой сам режет по словам.
- Тест границы `ptable-boundary` будет переписан. Замер скорости пока не нужен.
- Порядок: интерфейс, `measure`, стили и `draw` внутрь текстового содержимого, выделение и копирование на позициях, текстовый пакет вне `ptable`, кэш,
  своё содержимое якорей/уровня/Index, куски текста, подсветка Payload последней. Готовые подготовительные коммиты (фрагменты колонки модели, хук `paintCellBack`,
  цвета чипов в палитре) войдут в итог; хук `paintCellBack` будет заменён рисованием внутри текстового содержимого. Ошибочные промежуточные коммиты
  пользователь предложил слить в конце одним (`squash`).

## Снятие моста: решения пользователя по плану архитектора (2026-11-19, четвёртая сессия)

- **Высота строки — высота самой высокой ячейки**: каждая видимая колонка отвечает высотой своей ячейки в данной ширине (`measure().height`),
  строка берёт наибольшую, таблица ничего не прибавляет. **Вертикальные отступы — часть ячейки** (как `padding` у `<td>`): сверху и снизу в стиле
  колонки рядом с левым и правым, текстовая колонка по умолчанию берёт прежний 1 dip; `TableGeometry.rowPad` уходит. Поле над строкой (`margin`)
  остаётся у таблицы.
- **Выделение одно на таблицу**: начало и конец — (строка, колонка, позиция в ячейке). Часть каждой ячейки таблица считает на лету (между началом и
  концом — вся ячейка, у первой от позиции до конца, у последней от начала до позиции) и передаёт колонке готовый диапазон; что значит позиция,
  знает только колонка. Тип `Position` остаётся один (из `ptable/column.d`).
- **Конец выделения — между символами** (как курсор): диапазон `[from, to)`, пустое выделение `from == to`; включаемый конец старого кода уходит.
- **Перестановка колонок сбрасывает выделение**: номер колонки в позиции — её место на экране.
