# Логи в UTF-16

## Что

Текстовые логи в UTF-16 (little- и big-endian, с BOM и без) открываются любым текстовым
форматом: plain text, syslog, logcat и т.д. Раньше такой файл не открывался совсем: нулевые
байты делали его «бинарным», и ни один детектор его не принимал.

UTF-16 встречается в логах Windows: Windows PowerShell 5 пишет `>` и `Out-File` в UTF-16LE с
BOM, так же пишет `ERRORLOG` SQL Server и приложения .NET с `Encoding.Unicode`. Проверено на
сторонних тестовых файлах: десять строк с кириллицей, CJK, RTL,
суррогатными парами и символами, у которых один из байтов `0x0A` или `0x0D` (U+0A0A, U+0D0A…).

## Как устроено

- **Кодировку решает registry, а не форматы.** Детекторы смотрят данные как есть и, для
  UTF-16, в UTF-8. С BOM побеждает UTF-16, если его принял какой-то формат; иначе данные
  читаются как есть (бинарные байты могут совпасть с BOM). Без BOM UTF-16 угадывается
  (`guessUtf16`) и побеждает, только если как есть данные подошли хуже: ни одному формату или
  одной подсказкой расширения `.dlt`. Нулевые байты есть и у бинарных форматов, и DLT не
  должен стать «текстом в UTF-16».
  Признак: не меньше половины 16-битных единиц — ASCII (ноль в старшем байте), почти нет
  нулей с другой стороны и нет единиц U+0000.
- **Детекторы и `create` получают начало файла в UTF-8** (`utf8Head`). Ни один формат не
  изменился: они по-прежнему разбирают UTF-8.
- **Чтение — обёртка над текстовым форматом** (`inEncoding`). Она ищет строки в UTF-16 (конец
  строки — единица U+000A на чётном смещении, а не байт `0x0A`) и отдаёт `isRecordStart` и
  `decodeText` текст, переведённый в UTF-8 в буфер на стеке. Без аллокаций при декодировании;
  экземпляр неизменяем. Алгоритм записей (многострочные записи, предел длины, ожидание
  неполной строки) — один для UTF-8 и UTF-16: функции `TextFormat` стали шаблонами по
  кодировке, UTF-8 инстанцирует их как раньше.
- **Предел записи в UTF-16 — 2/3 `maxRecordLength` байт**: UTF-8 такой записи не длиннее
  `maxRecordLength`, на что опираются форматы и буфер `LogMessage`. Длинная строка режется
  между символами: суррогатная пара не разрывается.
- **Кодировка запоминается** в `FormatChoice.encoding` и в недавних файлах (`"encoding"`,
  только не для UTF-8). Незнакомое имя кодировки — формат определяется заново. Так же, если
  данные противоречат сохранённой кодировке (BOM или вид UTF-16 другой кодировки): файл по
  тому же пути могли перезаписать, и в неверной кодировке была бы испорчена каждая строка.
- **`scanRecords`, `recordAt` и `decode` у `TextFormat` — `final`**: обёртка UTF-16 идёт мимо
  них, и формат, переопределивший их, в UTF-16 молча работал бы иначе.
- **`text_encoding` лежит в `log_core`, а не в `log_core/text`**: кодировку хранит
  `FormatChoice` общего `log_format`, а он не должен зависеть от подпакета текстовых форматов.

## Что отвергнуто

- **Перекодировать весь файл во временный UTF-8.** Файлы до гигабайта, смещения индекса
  байтовые: пришлось бы держать копию на диске и пересчитывать смещения.
- **Кодировка в конструкторе каждого текстового формата.** Пришлось бы менять все форматы и
  их детекторы, а `create` получает только начало файла — UTF-8 для детекции или сырое.
- **Открывать UTF-16 «как текст по строчкам» без декодирования.** Получился бы мусор: NUL
  после каждого символа, строки LE начинаются с `00`, U+0A0A режет строку.
