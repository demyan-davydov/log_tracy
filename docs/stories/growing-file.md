# Растущий файл

Статус: сделано. Проверено на macOS (тесты и приложение). Код для Linux тот же, что для macOS
(POSIX), но на Linux не запускался. Код для Windows проходит проверку типов
(`ldc2 -mtriple=x86_64-pc-windows-msvc -o-`), но не запускался: машины нет. Ветка `growing-file` начата от
`index-facts`, которая ещё не слита в `master`. План прошёл ракурс архитектуры (2026-11-15), его
находки внесены ниже. Что вышло иначе, чем в плане, — в разделе «Как сделано».

## Что

Лог, который ещё дописывается (приложение пишет в файл, `dlt-receive` пишет в `.dlt`), должен
расти в таблице сам, пока он открыт. Сейчас `FileSource` отображает файл таким, каким он был при
открытии, и новых строк не видно.

Решения пользователя (2026-11-15):

- **Следить всегда.** Рост любого открытого файла подхватывается без включения. Размер файла
  проверяется раз в ~250 мс.
- **Держать низ.** Если таблица была прокручена до последней строки и текущей строки нет (или
  текущая — последняя), таблица едет за новыми строками, как `tail -f`, а текущая строка остаётся
  последней. Если пользователь прокрутил выше или выделил строку выше, прокрутка не трогается.
  Правило одно для главной таблицы и для таблицы поиска.
- **Хвост после паузы ~1 с.** Запись, которую обрезал конец файла, ждёт. Если файл не рос
  секунду, хвост отпускается. Статичный файл без перевода строки в конце покажет последнюю
  строку через секунду после открытия.
- **Потоки (DLT по TCP от dlt-daemon) — отдельная следующая фича.** Поток будет писаться в
  файл-спул на диске и открываться как растущий файл.

Модель под растущий источник уже готова: `ByteSource.complete`, проход вдогонку,
`IndexGrown` → `ContentGrown`, состояния видов (вид остаётся `ready` и считает строки), рост
таблицы скриптом (`list.grow()`). Всё это проверено на источниках-заглушках. Не хватает самого
источника, слежения за файлом и следования за низом.

### Что значит «хвост отпускается» для разных форматов

`complete()` передаётся сканеру как `final_` (`LogFormat.scanRecords`).

- **Текст.** Строка без перевода строки берётся записью. Если её потом допишут, продолжение
  придёт следующей записью: одна строка лога разрежется на две. Для писателей с полной
  буферизацией (stdio на C пишет блоками) это не редкость. Цена паузы в 1 с принята.
- **DLT.** Неполная запись при `final_` не берётся, а отбрасывается. Если её потом допишут,
  остаток пойдёт мусором до следующего storage header. У файлов `dlt-receive` storage header
  есть, так что теряется одна запись. Писатели DLT пишут запись целиком, поэтому пауза посреди
  записи — редкость.
- **Склейка частей** (сообщения, разрезанные приложением, `PartedFormat`): `final_` закрывает
  незакрытые сообщения. Часть, пришедшая после паузы, станет записью сама по себе. Пункт бэклога
  «Склейка частей в потоке без конца» этим отчасти решён: сообщение перестаёт ждать вечно.
- **Вложения** (передача файла в DLT): во время паузы незаконченная передача показывается
  «неполной», с новыми байтами снова «передаётся». Это правда на момент паузы. Отдельный
  признак «источник ещё может вырасти» не вводится: для пользователя разница не стоит второго
  флага.

## План

### 1. `MappedFile`, который растёт на месте (`utils/mapped_file`)

Контракт `ByteSource.data()`: более длинный срез с теми же байтами на том же месте. Поэтому
отображение не переезжает: под файл резервируется адресное пространство с запасом, файл
отображается в его начало, а новые байты — следом.

- **Запас:** `max(4 × размер, размер + 64 ГиБ)`. 64 слота по 64+ ГиБ — несколько ТиБ из 128 ТиБ
  адресов. Если резерв не дался (`RLIMIT_AS`, старая Windows), файл отображается как сейчас и не
  растёт. Если файл перерос запас, он просто перестаёт расти.
- **POSIX.** `mmap(PROT_NONE, MAP_PRIVATE | MAP_ANON | MAP_NORESERVE)` на запас, файл поверх него
  (`MAP_FIXED | MAP_SHARED`). Дескриптор файла остаётся открытым. `grow()`: `fstat`; если файл
  вырос, отображается только `[pageCeil(старая длина), новая длина)` со смещением
  `pageCeil(старая длина)`. Уже отображённые страницы не переотображаются: последняя неполная
  страница — разделяемая страница кеша файла, и дописанное в неё видно сразу. Поэтому читателям
  на других потоках ничего не грозит.
- **Windows.** Заглушки адресного пространства (`VirtualAlloc2` с `MEM_RESERVE_PLACEHOLDER`,
  `MapViewOfFile3` с `MEM_REPLACE_PLACEHOLDER`, Windows 10 1803+), функции берутся через
  `GetProcAddress`. Представление файла кладётся на `[0, floor64K(размер))`. Остаток и всё
  дописанное идут в закоммиченную частную память следом и заполняются `ReadFile`, не больше
  16 МиБ за один опрос, чтобы окно не ждало диск. Заменить частную память представлением, пока её
  читают другие потоки, нельзя без окна, где чтение падает.
  - **Путь потери переделывается.** Сейчас обработчик сбоя снимает представление на весь
    диапазон слота и резервирует его заново. Теперь сбоить может только представление, а частная
    память — нет. Обработчик заменяет только диапазон представления, ошибка `ReadFile`
    помечает файл потерянным. `close()` освобождает обе части.
  - **Цена:** дописанное держится в памяти (RAM или подкачка). Для растущего лога это приемлемо.
    Для фичи потоков нет: спул открывается почти пустым, и на Windows в памяти оказался бы весь
    поток, против правила «nothing loads a whole log into memory». Поэтому **условие фичи
    потоков на Windows** — представления для целых 64K-кусков дописанного вместо частной памяти.
    Записывается в бэклог как условие.
- **Регистрация в обработчике сбоев.** Охраняемый диапазон слота растёт вместе с отображением
  (атомарно меняется `end`). Длина среза публикуется атомарно (release), `data()` читает её с
  acquire.
- **Файл стал короче** (усечён): `grow()` замечает это заранее, не дожидаясь SIGBUS, и источник
  сообщает об усечении (шаг 4). Ротация переименованием (на месте файла новый) в первой версии
  не отслеживается: дескриптор смотрит на старый файл, который перестаёт расти. В бэклог.

### 2. `ByteSource` и `FileSource` (`log_core/byte_source`, `log_core/log_format`)

- В `ByteSource` добавляется `poll(MonoTime now)`. Метод узнаёт о дописанных байтах и о тишине
  источника. Время передаётся извне, чтобы тесты управляли часами. Пустая реализация нужна всем
  заглушкам: `MemorySource`, `GrowingSource`, `LosableSource`, тестовый источник
  `record_store` (и две заглушки `match_scan` на ветке `mcp`, при её слиянии).
- **`complete()` больше не «навсегда».** Новый смысл: «сейчас новых байтов не ждут, запись,
  обрезанную концом, можно отпустить». Источник может снова стать незавершённым, если пришли
  байты. Что было взято, остаётся. Переписываются комментарии `ByteSource.complete`, `final_` в
  `LogFormat.scanRecords` и контракт `scanRecords` в `.ai/knowledge/architecture.md`. Порядок
  «сначала `complete()`, потом `data()`» остаётся.
- **`FileSource`.** При открытии `complete = false` и запоминается время. `poll`: если файл
  вырос — `complete = false`, время запоминается заново. Если нет и прошла пауза
  (`quietPeriod` = 1 с) — `complete = true`.

### 3. Запись не меняет текст, когда файл дописан (`domain/index/record_store`)

Находка ракурса архитектуры, без неё план не работает. `Records.decode` отдаёт формату все
`data`, и текстовый `recordAt` ищет конец записи сам, до перевода строки. Хвост `"ab"`, взятый
записью после паузы, после дописывания `"c\n"` прочитается как `"abc"`, а `"c"` придёт ещё и
следующей записью. Строка меняется на месте под той же `dataVersion`, а это ломает контракт видов
(«rows appended in order, none moved»).

- `Records` отдаёт формату данные, ограниченные известным концом записи: смещением следующей
  записи, а у последней — `scannedBytes` на момент выдачи `Records`. Для сообщений, склеенных из
  частей (DLT, записи с длиной), граница — `scannedBytes`.
- Цена — ещё одно чтение смещения на декодирование. Замерить `bench_rows` против `master`.

### 4. Индекс и документ (`domain`)

- **Опрос — через индекс.** `LogIndex.poll(now)` → `RecordStore` → `ByteSource.poll`, под тем же
  `assert(!busy, "a pass is running")`, что у `behind()`. Источником владеет `RecordStore` (счёт
  ссылок с арендами), второго владельца у него не появляется. Правило «опрашивать, только пока
  прохода нет» проверяет код.
- **`LogIndex.behind`**: рядом с `holding && complete` добавляется
  `complete && scannedBytes < data.length` (хвост ждёт, а источник завершён). Нового состояния не
  нужно. Закрывается пункт бэклога «конец потока без новых байтов». Ручное обнуление `_seenBytes`
  в тесте `LogIndex: a source that grows...` уходит.
- **`LogDocument.dispatchEvents`**: если проход не идёт, источник не потерян, а с последнего
  опроса прошло 250 мс, вызывается `_index.poll(now)`, затем `startPassIfBehind` (уже есть).
  Часы подставляются тестами (по умолчанию `MonoTime.currTime`). `DocumentStore` опрашивает все
  документы, и те, у которых нет вкладки.
- **Формат пустого файла.** Если при открытии файл был пуст, а формат не выбран пользователем,
  формат определяется заново по первым байтам, когда они придут (`detectFormat`, затем путь
  замены формата, `FormatReplaced`). Иначе только что созданный `.dlt` или пустой лог навсегда
  получат формат, определённый по пустоте.
- **Пробуждение цикла окна.** Окно зовёт `dispatchEvents` на каждой итерации цикла
  (`MainWindow.onIdle`). Что итерация сама возвращается каждые 50–100 мс без ввода, измерено
  только на macOS, и Sciter этого не обещает (`.ai/knowledge/sciter.md`). Поэтому раз в 250 мс,
  пока открыт хоть один документ, окно будится через уже существующий механизм
  `SciterPostCallback`. Это 4 пробуждения в секунду, почти бесплатно.
- **Усечённый файл открывается заново** (решение пользователя: так ротирует `logrotate
  copytruncate`). `ByteSource.truncated()` → документ публикует `SourceTruncated` →
  `AppSession` открывает файл заново тем же путём, что `retryDocument` (формат прежний, фильтры
  восстанавливаются, документ заменяется в `DocumentStore`, держатели видят новое поколение), и
  зовёт скрипт `onDocumentReopened(id)`. Скрипт сбрасывает таблицы, строку поиска и панель
  фильтров. Код из обработчика кнопки «Повторить» выносится в метод, который зовут оба пути.
  Якоря и поиск теряются, как при «Повторить». Если открыть заново не удалось, документ
  показывается потерянным с причиной.
- **`DocumentState`** другим держателям (MCP) не говорит, что лог растёт. MCP ещё не слит. Поле
  добавить при слиянии `mcp`: в бэклог.

### 5. Следование за низом (скрипт)

- Правило — чистая функция рядом с уже существующими решениями о росте списка (`growStep` в
  `resources/list-navigation.js`, `tableStep`/`jumpStep` в `resources/pane-state.js`), тесты в
  их файлах `tests/js`.
- **Только для роста готового вида.** `step.grow` бывает и при загрузке, фильтре и поиске. Если
  следовать там, большой файл, у которого в начале видна «последняя» строка, утащит таблицу в
  конец загрузки. Правило получает статус вида и следует только за ростом вида в `ready`
  (`ContentGrown`).
- `view-table.js` на `step.grow` спрашивает его и прокручивает (без анимации) или нет.
- Проверка в приложении через `/app`: открыть файл, дописывать в него из скрипта, смотреть, что
  таблица растёт, держит низ и не трогает прокрутку, если пользователь ушёл выше, а при открытии
  большого файла остаётся вверху.

### Тесты

- `MappedFile`: дописать файл, `grow()` — срез длиннее, тот же адрес, старые байты на месте;
  файл короче — `lost`; пустой файл, который потом вырос.
- `FileSource.poll` с подставными часами: незавершён сразу, завершён после паузы, снова
  незавершён после роста.
- `Records`: хвост, взятый после паузы, после дописывания читается как раньше.
- `LogIndex.behind`: завершённость без новых байтов запускает проход.
- `LogDocument`: настоящий файл, дописанный во время работы. Новые записи видны,
  `ContentGrown` пришёл, хвост без перевода строки появился после паузы. Пустой файл, в который
  потом записали DLT, определён как DLT.
- `AppSession`: усечённый файл открыт заново в той же вкладке, фильтры на месте, скрипту
  сказано.
- JS: правило следования (готовый вид, внизу — следует; при загрузке — нет; выше — нет).

### Порядок коммитов

1. Граница записи в `Records` (полезна и без роста, проверяется на заглушках).
2. `MappedFile` растёт: POSIX, затем Windows с новым путём потери.
3. `ByteSource.poll`, новый смысл `complete`, `FileSource` с паузой.
4. `LogIndex.poll`/`behind`, опрос в `LogDocument`, пробуждение окна, формат пустого файла.
5. Усечённый файл открывается заново.
6. Следование за низом.
7. Документы.

### Риски

- Код для Windows и Linux на этой машине (macOS) только пишется. Linux можно собрать и проверить,
  если найдётся машина или контейнер. Windows без машины не проверить, CI нет. Путь Windows
  самый сложный (заглушки, частная память, новый путь потери).
- `MAP_FIXED` поверх своего резерва безопасен только внутри него. Запас резервируется один раз и
  не освобождается до `close()`.

## Как сделано

Порядок плана выдержан. Отличия и то, что нашлось по ходу:

- **Опрос — отдельный интерфейс `PolledSource`, а не метод `ByteSource`.** `FileSource`
  реализует оба, `RecordStore.poll` находит возможность приведением типа, как `PartedFormat` и
  `TransferringFormat`. Шесть заглушек тестов не пришлось трогать.
- **Пробуждение цикла окна не добавлено.** События индекса и сейчас доходят до окна только
  потому, что итерация цикла сама возвращается каждые 50–100 мс (измерено на macOS). Опрос
  держится на том же. Если на Windows или Linux это не так, там встанет и уже существующий
  прогресс операций, поэтому это общая проверка — пункт бэклога «Цикл окна без ввода».
- **Граница записи в `Records`** стоит +1,2 % на строку при прокрутке (`build.mjs bench`, лог
  DLT 256 МБ: 125,4 → 126,9 нс на строку главного вида). Это ещё одно чтение смещения.
- **Две ошибки, которые вскрыл незавершённый файл:**
  - Нули потерянного файла (сбой страницы заменяется нулями) сканер без `final_` принимал за
    начало записи, которая ждёт продолжения. Загрузка считалась законченной (`tailWaits`), и
    потеря файла во время загрузки заканчивала её успехом. Теперь `scanOffsets` проверяет потерю
    сразу после чтения пачки.
  - Проход успевал разобрать первые байты пустого файла форматом по имени до того, как формат
    определялся заново, а `RecordStore.replaceFormat` не принимает формат других записей. Пока
    формат ждёт байтов, проходы придерживаются (`startPassIfBehind`), а `replaceFormat` принимает
    любой формат, пока ни один байт не разобран.
- **Вложения DLT.** Незаконченная передача считается «неполной» только после паузы. Тест
  вложений ждёт её с подставными часами.
- **Часы в тестах документа** ставятся после открытия файла (`openWithTestClock`): `FileSource`
  запоминает настоящее время открытия, и часы, поставленные раньше, не набирали паузу.
- **Тесты.** Тесты `Records`, `MappedFile`, `FileSource`, правила следования и сессии
  (открытие заново) сначала падали на заглушках. Тесты документа (рост, усечение, формат пустого
  файла) написаны до кода, но до реализации не запускались: их падения не видел. Тест индекса
  «a source that grows» без ручного обнуления `_seenBytes` — тоже.
- **Windows.** Сделано по плану: заглушки адресного пространства, представление на целые куски
  по 64K, остаток и дописанное — в частную память `ReadFile`, не больше 16 МиБ за `grow()`.
  Ошибка чтения помечает файл потерянным своим флагом (`_readFailed`), а не состоянием слота
  обработчика сбоев: представление при этом остаётся, и обработчик, увидев «потерян», не смог бы
  подменить его страницы. Тесты роста `MappedFile` вынесены из `version (Posix)`: на Windows
  маленькие файлы читаются в частную память целиком, поэтому их можно обнулить (файл с
  представлением Windows укоротить не даёт). Запустить их негде.
- **Проверка в приложении** (`/app`, macOS): таблица растёт и держит низ, текущая последняя
  строка остаётся последней, строка выше и прокрутка вверх не трогаются, хвост без перевода
  строки приходит после паузы и не меняется, когда строку дописывают (продолжение — следующей
  записью), обнулённый файл открывается заново и растёт дальше.

## Ревью ветки (ракурсы и `/code-review`)

Ракурс производительности оборвался на лимите расходов и не дал отчёта: при следующем ревью
его стоит прогнать. Исправлено:

- **Формат пустого файла — открытием заново, а не заменой на месте** (ракурс архитектуры).
  Замена формата задумана для формата тех же записей: держатели документа (`DocumentFilters`)
  помнят колонки формата, с которым открыли. Текстовый лог, определённый как DLT на месте, не
  принимал правила по ECU или AppId. Теперь документ публикует `ReopenWanted` (одно событие на
  усечение и на найденный формат), и сессия открывает файл заново выбранным форматом. Смягчение
  `RecordStore.replaceFormat` убрано.
- **Медленные первые байты** (`/code-review`): пустой файл, в который пишут понемногу без пауз,
  ждал 4 КиБ. Теперь формат определяется и через `detectWait` (0,5 с) после первых байтов.
- **Не удалось открыть заново** (все три ракурса и `/code-review`): вкладка молча замирала на
  старых строках. Теперь она показывает вид потерянного файла с «Повторить» — обещание плана.
- **«Держать низ»** (ракурс UX и `/code-review`):
  - выделенный диапазон до последней строки больше не схлопывается: текущая строка переезжает к
    новому концу, только если выделена она одна;
  - другая таблица за этими переездами не следует (`rowChosen` не зовётся: выделение двигает
    скрипт, не пользователь);
  - таблица, которая не видна (вкладка или страница скрыта), не решает по геометрии без
    раскладки: `VirtualDltTBody.endState()` отдаёт null, и она остаётся на месте. Снимок «до
    роста» делает сама таблица, а не `ViewTable` по внутренностям `vlist`.
- **Документы:** номера правил `ux.md` в бэклоге и двух историях, `ui.md`, шапки модулей.
- **Исправление «нули потерянного файла»** своего теста не получило: его поймал существующий
  тест «LogDocument: losing the file while loading fails the load», который упал после того, как
  `FileSource` стал незавершённым.

Отложено в бэклог: уведомление об открытии заново (решение за пользователем), усечение во время
прохода (не проверено).

Не принято:
- **Часы `FileSource` от первого опроса, а не от открытия** (ракурс архитектуры). Это убрало бы
  `openWithTestClock`, но сдвинуло бы паузу статичного файла на время загрузки. Помощник в тестах
  дешевле.
- **Логика по пустоте строки ошибки `reopen`** (ракурс правил). Тот же контракт, что у
  `retryDocument`, текст не сравнивается.
- **Запросы во время ожидания формата сообщаются законченными** (`/code-review`). Ожидание теперь
  не дольше 0,5 с после первых байтов, а файл потом открывается заново с восстановленными
  фильтрами.

## Решено после ревью

**Файл стал короче** (`logrotate copytruncate` копирует живой лог и обнуляет его): открывается
заново с начала автоматически, тем же путём, что «Повторить» (шаг 4). Второй вариант — считать
его потерянным — отвергнут: при ротации пришлось бы каждый раз нажимать «Повторить».
