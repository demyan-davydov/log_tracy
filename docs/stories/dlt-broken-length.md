# DLT: сломанная длина не накрывает следующие записи

## Что

- Запись DLT в файле со storage header'ами, у которой длина в стандартном заголовке больше
  настоящей, больше не прячет следующие записи. Если сразу за ней нет storage header'а (и это
  не конец данных и не начало заголовка, который ещё дописывается), запись заканчивается на
  первом storage header'е внутри неё.
- На 100 МБ с 0,1% порчи всех видов (`gen-log --format dlt --size 100M --corrupt 0.1%`) индекс
  находит 872 435 записей из 872 801, раньше — 839 491. Только порча длины
  (`--corruptions bad-length`, 867 сломанных): 871 869 вместо 760 920.

## Почему так

- **Проверка за O(1), поиск только в сломанной записи.** Побайтный поиск шаблона в каждой
  записи и тот же поиск через `memchr` замедляли сканирование в разы; проверка «за записью
  storage header или конец данных» на индексации целого файла почти не видна. Замеры и их
  условия — `docs/experiments/2026-11-10-dlt-broken-length.md`. Ложных срабатываний на
  payload целых записей нет: в них не ищут.
- **Обрезка в `layoutOf` (`cutAtNextHeader`), а не в `scanRecords`.** Индекс хранит только
  смещения, `recordAt` вычисляет длину заново: обрезанная только сканером запись показала бы
  в payload следующие записи, они шли бы дважды. Хранить длину в индексе — больше 8 байт на
  запись. Функция без состояния: её зовут воркеры параллельно.
- **Поиск с конца своего базового заголовка.** Шаблон в собственных storage header'е и
  стандартном заголовке не обрезает запись. Если обрезанная запись короче заголовков, о которых
  говорят её флаги, она негодна и пропускается, как любая запись короче своих заголовков:
  годность считается по меньшей из длин, заявленной и обрезанной (находка `/code-review`).
  Найденный заголовок должен уместиться в данных целиком
  (`findNextStorageHeader`), поэтому поиск идёт до конца записи плюс 15 байт.
- **Хвост из 1–3 байт `DLT` за записью — начало заголовка.** В растущем файле следующий
  заголовок может быть дописан не до конца: такую запись не режем.
- **Слишком короткая длина не исправляется.** За записью нет заголовка, внутри — тоже: запись
  остаётся своей длины, сканер ищет следующий заголовок дальше, как и раньше. Длина короче
  заголовков (генератор пишет 0..3) делает запись негодной, она теряется — одна.
- **Декодер не меняли.** Он режет payload по концу переданного среза (версия 2 — по меньшему
  из длины и среза), обрезанная запись декодируется без выхода за границы.

## Что не ловится

- Ложный конец записи попал ровно на настоящий storage header. Длина портится случайно
  до 65535, записи ~120 байт: на 867 сломанных длин в файле генератора такая одна, она
  накрыла 516 записей. Проверка за O(1) такую запись не отличит от целой; нужна проверка
  правдоподобия содержимого (см. `docs/backlog.md`).
- Длина за концом данных: при `final_` сканер, как и раньше, ищет заголовок внутри и теряет
  саму сломанную запись (но не следующие); без `final_` ждёт, что запись ещё допишется.
