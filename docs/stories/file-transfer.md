# DLT: файлы, переданные внутри лога

Ветка: `file-transfer`.

## Что

- Приложение может передать в DLT целый файл: картинку, запись звука, архив трасс, core dump.
  Нужно находить такие файлы в логе, показывать их список, открывать и сохранять.
- Первый шаг сделан в бэкенде: файлы находятся при загрузке, скрипт получает их список и
  сохраняет файл. Интерфейса списка и показа файлов ещё нет (`docs/backlog.md`).

## Как файлы хранятся в DLT

- В стандарте AUTOSAR понятия «файл» нет. Есть только кирпичики: аргумент RAWD у
  verbose-сообщения (байты; сообщение DLT не длиннее ~64 КБ), payload non-verbose-сообщения
  (байты по ID, смысл знает FIBEX) и network trace (MSTP = NW_TRACE, кадры шин; большие режутся
  сегментами NWST/NWCH/NWEN, в логах пользователя их нет — см. `joined-parts.md`).
- Файлы передаёт протокол COVESA dlt-daemon (`dlt_filetransfer.c`, вызовы
  `dlt_user_log_file_complete`, `_header`, `_data`, `_end`). Это обычные verbose-сообщения;
  первый и последний аргумент — строка-маркер:

  | Сообщение | Аргументы |
  |---|---|
  | FLST, начало | `"FLST"`, serial (uint32), имя файла (string), размер (uint32), дата создания (string), число пакетов (uint32), размер буфера (uint32), `"FLST"` |
  | FLDA, данные | `"FLDA"`, serial, номер пакета с 1 (uint32), данные (RAWD), `"FLDA"` |
  | FLFI, конец | `"FLFI"`, serial, `"FLFI"` |
  | FLER, ошибка | `"FLER"`, код ошибки, errno, затем serial, имя, размер, дата, число пакетов (и, возможно, размер буфера) — или одно имя (возможно, после подписи), если файл не прочитать |
  | FLIF, сведения | имя, размер, дата, число пакетов, без данных |

- Serial связывает пакеты одного файла. Между пакетами идут чужие сообщения, несколько файлов
  могут передаваться одновременно. Файл — это RAWD всех FLDA по порядку номеров. Размер
  в uint32: файлы меньше 4 ГБ.
- Тип файла протокол не хранит: только имя. Тип узнаётся по расширению и магическим байтам.
- FLST, FLDA и FLFI сверены с логом пользователя и с плагином dlt-viewer
  (`plugin/filetransferplugin/globals.h`). FLER в логах пользователя не встречался, и в
  источниках он разный: плагин dlt-viewer читает пять аргументов (код, errno, имя), а
  dlt-daemon, по памяти, пишет и serial с полями файла, и размер буфера, и подпись перед
  именем. Поэтому FLER разбирается по видам аргументов, а не по их числу. FLIF не разбирается.

## Выводы для дизайна

- Искать байты маркеров нельзя: они встречаются в данных и в ID контекста. Сообщение передачи —
  verbose, первый аргумент — строка из 4 байт `FL??`; это дешёвая проверка, как у склейки частей.
- Лог бывает гигабайтным, файл в нём — сотни мегабайт: при индексации хранится только каталог
  (serial → FLST, смещения FLDA, состояние), байты файла читаются по запросу.
- Неполный файл — обычный случай (конец записи, потерянные пакеты): показывать, сколько его есть
  (32 590 из 116 681), и решить, что с ним можно делать.
- Файл может оказаться разрезан между кусками записи (разными `.dlt`) — вопрос на потом.
- Файл не обязательно медиа: в найденном логе это `tar.lz4`. Показ выбирается по типу.

## Решения первого шага: чтение и список файлов

- **Каталог передач строится при индексации**, как склейка частей: `RecordStore` спрашивает
  формат о каждой записи дёшево, полный разбор — только прошедших. Отдельного прохода по
  логу нет, список растёт, пока файл грузится. Отвергнут отдельный параллельный проход по
  запросу: каждый раз читает весь лог, а список пуст, пока проход не кончится.
- **Один дешёвый вопрос на запись, а не по вопросу на интерфейс.** Сначала у
  `TransferringFormat` была своя проверка `mayBeTransfer` рядом с `mayBePart` склейки: индекс
  смещений стал медленнее на 28% (60 → 77 мс на сгенерированном DLT в 256 МБ) — половина на
  втором виртуальном вызове на запись, половина на втором обходе заголовка. Теперь оба
  интерфейса расширяют `MarkedFormat`, и формат отвечает одним `marksOf` битами
  `RecordMark` (часть, передача); `DltFormat` обходит заголовок один раз
  (`parser.findVerboseStart`) и по числу аргументов делает одну из проверок: у части один
  аргумент, у сообщения передачи три и больше. Пачка без передач в каталог не заглядывает
  (`Bunch.anyMarks`).
- **Общий обход сначала стоил +8.5%** и без проверки передачи: с прежней проверкой частей в
  `marksOf` разница пропадала. Помогли встраивание пути версии 1 (`pragma(inline, true)`,
  обход версии 2 — отдельной функцией: целиком LDC её не встраивал), одна проверка флагов и
  длины, как была в проверке частей, и `ref` вместо `out` (без обнуления структуры на каждой
  записи). Не помогло чтение одного байта флагов вместо всего `typeInfo` в проверке передачи —
  откатили.
- **Цена.** Сгенерированный лог (256 МБ, только verbose с одним текстом — для каждой записи
  проверка частей идёт целиком): индекс смещений 60.4 → 62.7 мс (+3.8%, в пределах разброса),
  фильтр и поиск без изменений. Лог пользователя с передачей (459 МБ): 89.3 → 94.6 мс (+5.9%);
  без проверки передачи разница +1.3%, то есть остальное — проверка сообщений с тремя
  аргументами и больше и полный разбор 32 590 пакетов этого лога, работа самого каталога.
- **Протокол знает только формат** (`formats/dlt/file_transfer`): разбор FLST, FLDA, FLFI, FLER
  в `TransferMessage`. Домен видит его через интерфейс `TransferringFormat` (`log_core`), как
  `PartedFormat`; текстовые форматы его не реализуют.
- **Сообщение передачи** — verbose-сообщение типа log, первый и последний аргументы — один и
  тот же маркер, как проверяет плагин dlt-viewer. FLIF (только сведения о файле, без данных)
  пока не разбирается. FLER: если после кодов идёт число, это serial и поля файла (что за
  ними — размер буфера — не важно); иначе это имя файла, которого не прочитать (последняя
  строка перед маркером: подпись `"Filename:"` перед ним может быть, а может и не быть).
- **Каталог хранит только числа**: на передачу — номер записи FLST, serial, размер, число
  пакетов, сколько пришло и сколько подряд с первого, состояние; на пакет — смещение FLDA в
  логе. Правила каталога (serial, последняя открытая передача, нумерация с 1) записаны в
  контракт `TransferMessage`: другой протокол с другими правилами потребует их в каталоге. Имя и дата читаются из записи FLST, когда их спрашивают. Файл на 116 тысяч пакетов —
  около 2 МБ каталога.
- **Ключ — передача, а не serial**: тот же файл, отправленный дважды, приходит с тем же serial.
  FLDA и FLFI относятся к последней открытой передаче с их serial. FLDA без FLST (лог начался
  посреди передачи) открывает передачу без имени.
- **Байты файла не копируются**, пока их не попросили: они уже лежат в отображённом логе.
  Сохранение пишет пакеты подряд с первого до первого пропущенного (или пришедшего не по
  порядку): у неполного файла сохраняется начало — у `tar.lz4` и оно полезно.
- **Временной папки пока нет**: она понадобится, чтобы открыть файл внешней программой.
- **Строки FLDA в таблице остаются как есть.**
- Скрипт: `backend.attachments(docId)` — список, `onAttachmentsChanged(docId)` — каталог
  изменился, `backend.saveAttachment(docId, id, path)` — сохранить. Обработчик в скрипте пока
  пустой.
- **Изменение каталога — событие документа** (`AttachmentsChanged`, перезаписываемое): проход
  индекса публикует его, когда изменилось число принятых сообщений передач или лог дочитан до
  конца (файл без конца становится неполным). Сначала сессия опрашивала штамп документа в
  каждом цикле окна; ревью (архитектура, производительность) отметило второй путь мимо шины
  событий и мьютекс индекса каждого документа на каждом цикле — заменили событием. У лога без
  передач события нет.
- **Файл пишет сессия, домен отдаёт байты** (`Document.writeAttachment` с делегатами). Сначала
  файл писал `LogDocument`; ревью отметило, что запись файла пользователя живёт в `ui` (экспорт
  фильтра), и что сбой посреди записи поверх существующего файла терял и старый. Теперь
  `AppSession.saveAttachment` пишет в `<path>.part` и ставит его на место в конце: при сбое
  старый файл остаётся, недописанный удаляется. Файл создаётся, только когда есть что писать.
  У всех ошибок сохранения один шаблон «Не удалось сохранить файл: {reason}»; пропавший лог —
  «журнал больше недоступен», а не «файл».
- **Сохранение идёт синхронно**, в вызове скрипта: 33 МБ — 62 мс, целый файл в 119 МБ — около
  0,2 с на SSD с тёплым кэшем, на медленном диске — дольше. Список пакетов берётся под замком
  индекса, читается и пишется вне его. Фоновое сохранение с прогрессом — с интерфейсом.

## Проверка на логе пользователя

`Offline_244-..._Konv.DLT` в запущенном приложении (`scripts/app.mjs`): после загрузки
`getAttachments` дал одну передачу — `trigger_79_HU_20251103_101946_CAN.tar.lz4`, 119 480 325
байт, 116 681 пакет, пришло и подряд 32 590, состояние `incomplete`, запись 1 840 918 — это
строка FLST. `saveAttachment` записал 33 372 160 байт (32 590 × 1024) за 62 мс; `lz4 -dc | tar t`
читает из сохранённого начала список файлов архива.

## Открытые вопросы

- Строки FLDA в таблице: сворачивать передачу в одну запись «файл X, N пакетов» (как склеенные
  части) или оставлять как есть и показывать файлы отдельным списком.
- Неполный файл: сохранять начало молча, с пометкой в имени или спрашивать.
- Что Sciter умеет показать сам (картинки — да; видео и звук — проверить), а что открывать
  внешней программой.
